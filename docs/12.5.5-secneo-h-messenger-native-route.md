## 一、14 组受保护 DEX 元数据里找不到 H.gha/ghc 的符号调用

本次对 `libdatajar.so` 中所有已恢复的 **14 组**片段逐组执行原有 `carve` 严格验证，先重建含遮蔽字符串 ID 的完整 string_id 指针序列，再读取类型表、方法表和类定义表。

| 检查范围 | 已验证数量 |
| --- | ---: |
| DEX 元数据片段 | **14** |
| 类定义 | **101,716** |
| 类型 ID | **133,981** |
| 方法 ID | **758,948** |
| 精确 `Lcom/secneo/apkwrapper/H;` 类型 | **0** |
| 精确 `gha` 或 `ghc` 字符串 | **0** |
| 指向该 H 类型的 `gha/ghc` 方法引用 | **0** |

因为这些片段的类型表缺少精确的 `H` 描述符，其方法引用表不能编码对该类 Native getter 的直接符号调用。这一结论**仅适用于已经恢复的 14 组元数据**。原始加固 DEX 后续动态加载、运行时生成/替换类、反射、JNI 自身的间接分发仍未被排除。这些片段中确实有 `DECApp` / `DeviceEnvironmentCheck` 的不同引用；不能因存在 DEC 类型就把它与不存在的 H 方法符号强行关联。

## 二、原版 JNI_OnLoad 中同一张六项注册表

原始内层 ELF 在 `0x16118` 设置 `RegisterNatives` 的项数为 **6**，在 `0x164F8–0x164FC` 使用同一运行时类引用和 JNIEnv 虚表完成绑定。每个方法名及签名均从原版 ARM64 `LDRB` 立即数与可打印 ASCII 表逐字节还原，并与原始 `classes.dex` 的 `method_ids`、`class_data` 和 `access_flags` 一一核对。

| Java 方法 | DEX method_id | JNI 函数地址 | 原版直接证据 |
| --- | ---: | --- | --- |
| `gha(String): int` | 138 | `0x367A4` | 调 `0x2682C`，返回状态低八位 |
| `ghc(String): long` | 139 | `0x36814` | 调 `0x2682C`，返回记录标识 |
| `gah(): Object[]` | 135 | `0x3687C` | `0x3697C` `fopen`、`0x36A74` `fgets`；构造 Java 对象结果 |
| `sha(String,int): void` | 146 | `0x36F14` | JNI 取字符串后于 `0x36F48` 直接跳向 `0x26BC0` 记录更新函数 |
| `he(int): void` | 141 | `0x36F4C` | 根据整数参数和配置位选择原生处理/终止分支 |
| `gv(): int` | 140 | `0x3714C` | `mov w0,#0x33E`，返回整数 **830** |

这六项是**同一张注册表的完整内容**；原版 H 类中还有别的 Native 声明和注册序列，不能把这里的六项当成整份 APK 的 Native 方法总数。除 `he` 为 `private static native`（`access_flags=0x10A`），其余五项为 `public static native`（`0x109`）。

其中 `sha` 已能静态连接到此前恢复的 `envc.push` 文件记录更新路径。对于 `he`，原版 `0x36F64` / `0x36F70` 分别比较参数 `0x1F8` 和 `0xE1E`，再测试运行时对象的 `+0x17C` bit0、`+0x17D` bit6 等配置位；其部分后续路径包含 `getpid`、内部函数 `0x2612C`、`_exit(3)`，另外存在低地址异常跳转指令。能证明原版机器码具有这些分支，**不能把它们等同于某轮设备上发生的退出或先前 `0x978` 崩溃**。

## 三、原版 Java 消息处理直接接入 he(int)

在基础 `classes.dex` 中，不需要通过字符串或反射推测：存在以下**可按真实 invoke-static 方法 ID 核对**的调用链：

```text
com.secneo.apkwrapper.H$a.handleMessage(Message)
    Message.what == 1000
    Message.arg2 -> H.c(int)              DEX 指令 0x4258

H.c(int)
    invoke-static H.he(int)                DEX 指令 0x4B1A

H.he(int)                                  DEX method_id 141
    JNI RegisterNatives -> 0x36F4C        内层 ELF
```

具体原始 DEX 证据：

- `H$a.handleMessage` 的 `code_item=0x41FC`，`0x4226` 通过 field_id 6 取得 `Message.what`，`0x422A` 构造整数 `1000`，`0x422E` 是 `if-eq`；命中该消息类型后，在 `0x4254` 从 field_id 4 读取 **`Message.arg2`**，`0x4258` 调用 `H.c(int)`（method_id 128）。
- `H.c(int)` 的 `code_item=0x4AF0`，`0x4B1A` 是 `invoke-static`，方法索引 **141**，即 `H.he(int)`。
- 对该基础 DEX 已验证的 **65 个含代码的方法项**进行 16 位对齐 `invoke-*` 候选扫描：在上述六项 Native 中只命中 `H.he` 的这一个直接调用点。此项属于固定样本范围的静态扫描，不覆盖动态 DEX、反射或其他原生入口。

进一步定位了发送端 `Lcom/secneo/apkwrapper/b;->onServiceConnected(...)`（`code_item=0x518C`）：

1. `0x51FA–0x51FE`：构造 `what=1000` 并调用 `Message.obtain(Handler,int)`。
2. `0x5206–0x520E`：调用 `Process.myPid()`，将结果赋给 **`Message.arg1`**（field_id 3）。
3. `0x5212–0x521A`：获取 `H.a()` 的 `Messenger` 并赋给 **`Message.replyTo`**（field_id 5）。
4. `0x521E–0x5226`：取得 `H.b()` 的 `Messenger`，通过 `Messenger.send(Message)` 发送。

此外，`H.<clinit>` 的 `code_item=0x427C`，在 `0x42FE` 使用 `new-instance`（type_id 50）构造 `Lcom/secneo/apkwrapper/b;`，`0x4302` 通过 method_id 154 调用 `b.<init>()`。这把 ServiceConnection 对象的创建进一步绑定到原版 H 类初始化；其确切 `bindService` 发起位置、远端 Service 的实现仍未恢复。

该发送流程使用通过 `IBinder` 构造的 Messenger，反映出原版存在服务连接后的消息通信方案。**发送端填的是 `arg1`，接收端传给 `he` 的是 `arg2`**；现有原始基础 DEX 没有直接证明是谁、在何时赋予接收消息的 `arg2` 数值，也没有设备日志证明某一条消息实际往返。不能因此断言 `he` 收到了本机 PID 或某一固定代码。

只读验证入口：[Messenger → H.he 调用链审计](../tools/audit_h_messenger_he_callchain.py)，配套[合成回归测试](../tests/test_audit_h_messenger_he_callchain.py)。

## 四、研究边界及下一步

**本轮已经闭合的静态联系**：原版服务连接回调构造 Messenger 请求及回复通道；`H$a.handleMessage` 在收到 `what=1000` 的消息时向 `H.c` 传入 `arg2`；`H.c` 直接调用 Native `H.he`，原生函数地址 `0x36F4C`。另可证明 `H.sha(String,int)` 为原版 `envc.push` 更新函数提供了 Java 可调用入口。

**尚未闭合**：与这条 Messenger 方案交互的远端 Service 具体实现、回复 `arg2` 的值和来源、`H.he` 的真实执行分支，以及 `DeviceEnvironmentCheck.startCheck()`、`DECMsgDialog` 与此链的任何直接联系。14 组已恢复 DEX 中缺少 `H` 方法引用只能排除那一限定范围的直接符号调用。
