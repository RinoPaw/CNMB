## 一、真实原始 ELF 中的完整直接 JNI SetStaticObjectField 加载位置

以前已从原版 JNI 指令恢复 `sw(Context,int)`、`bs(Context,int)` 在 `GetStaticFieldID`、`NewStringUTF` 后通过 `SetStaticObjectField` 写入 `H.PC_FLAG:Ljava/lang/String;`。当时尚未统计完整原生代码段里是否有其它相同形式的静态字段写入。

这次依据**真实 ELF64 节区表**定位内层 ELF 的 `.text` 节区：

| 属性 | 原版值 |
| --- | --- |
| ELF 虚拟地址 | `0xFA00` |
| 文件偏移 | `0xFA00` |
| 节区大小 | `0xE0358`（**918,360 字节**） |
| 节区属性 | `SHT_PROGBITS`、`SHF_EXECINSTR` |

在整个节区内逐条检查 4 字节对齐的 AArch64 机器字，搜索使用**64 位无符号立即数寻址**的 `LDR Xt,[Xn,#imm12*8]`，其中 `imm12=0x4D0/8=154`。JNI `JNINativeInterface` 的 `SetStaticObjectField` 虚表项对应偏移 `0x4D0`。原版实际恰好有两处匹配：

| ELF VA | 原版机器字 | AArch64 指令 | 后续调用 |
| --- | --- | --- | --- |
| `0x2C5D8` | `0xF9426908` | `ldr x8,[x8,#0x4d0]` | `0x2C5E0: blr x8` |
| `0x2CAB8` | `0xF9426908` | `ldr x8,[x8,#0x4d0]` | `0x2CAC0: blr x8` |

根据同一原版代码中恢复的 JNI 方法名、字段名和参数寄存器，这两处分别对应 `sw`、`bs` 的 `PC_FLAG` 写入链。其完整字段名 `PC_FLAG` 和 JNI 类型 `Ljava/lang/String;`，也由**两段不同可打印字符表基址下各 25 条真实 LDRB**独立构造，避免了单纯看到相同偏移就猜测调用语义的问题。

## 二、写入内容、先决条件与初始值

原版 `sw` 的 `0x2C4A4` 为 `orr w3,w21,#1`，对应新值 `原参数 | 0x01`。原版 `bs` 的 `0x2C97C` 为 `orr w3,w22,#2`，对应新值 `原参数 | 0x02`。两段都使用 `%d` 格式化整数，经 `NewStringUTF` 包装成 Java String 后调用 `SetStaticObjectField`。本次独立验证的机器字分别为 `0x320002A3`、`0x321F02C3`，两个后续 `blr x8` 为 `0xD63F0100`。

两条写入路径都有前置条件：

- `sw` 的原生入口 `0x2C46C`：传入 bit0 为 1 就提前返回；若允许继续，还要通过运行时 `+0x0C` 和 `/proc/<当前PID>/cmdline` 身份守卫。
- `bs` 的原生入口 `0x2C90C`：传入 bit1 为 1 就提前返回；后续同样要求身份守卫和运行时 `+0x0C` 字节非零。

在原版 `H.<clinit>`，`PC_FLAG` 初始化为字符串 **`"255"`**，因此两个入口的对应位都为 1，**此初始值下不会进入各自的字段写入指令**。即使将来通过其他途径改变了标志并满足守卫，本轮找到的两个赋值公式也只能将 bit0/bit1 设置为 1，不能清除对应位。尚未发现清除位的直接证据。

## 三、排除范围必须准确

**已排除的具体形式：** 这份固定哈希原版内层 ELF 的全部 `.text` 中，除了 `0x2C5D8` 和 `0x2CAB8`，不存在第三处使用 `LDR Xt,[Xn,#0x4D0]` 这一直接指令形式读取 `SetStaticObjectField` JNI 表项的调用点。

**没有排除的形式：** 将 JNI 函数指针通过计算偏移或其他寻址指令得到、把指针存入数据结构后再间接调用、复用另外的包装函数、其他 SO 的写入、Java 反射、动态加载或运行时生成的代码。这一静态搜索也无法判断对象在设备上的真实字段值、某个调用是否实际执行，或是否存在动态代码清除低位的情况。因此本报告不会将「无第三处这种指令」扩大为「PC_FLAG 绝不可能被其他代码修改」。

基础 `classes.dex` 的静态代码中已确认一次 `sput-object H.PC_FLAG`（`0x42F0`）和两次 `sget-object`（`0x4BDA`、`0x4C36`）。其作用域仅限原始基础 DEX 的 65 个代码项。将这份结果与本次内层 ELF 全 `.text` 扫描结合后，得到的是**两个互补、但都具有明确边界的静态证据集**。它们尚不能给出默认设备执行过 Messenger 绑定、收到 `Message.arg2` 或触发 `DECMsgDialog` 的证据。

## 四、复核方式

本次提交的 [`audit_inner_pc_flag_setter_census.py`](../tools/audit_inner_pc_flag_setter_census.py) 使用 Python 标准库独立读取原版 ELF64 节区表，强制检查 SHA-256、`.text` 地址与长度、每条直接 vtable 指令和两个 ORR 操作，再通过既有字符表审计验证字段名、签名。支持原版 base APK 和私有诊断 ZIP，拒绝其它版本样本。[合成单测](../tests/test_audit_inner_pc_flag_setter_census.py)检查 ELF 结构、vtable 立即数、区间边界、拒绝变异和原版指令常量。

```powershell
python .\tools\audit_inner_pc_flag_setter_census.py .\path\to\original-base.apk
```

原始商用 APK 与恢复内层 ELF 不上传公开仓库。下一步优先定位其它库或动态代码有没有清除 `PC_FLAG` 位的写入来源，并用实际设备数据而非推测确认是否发生过一次 `IsoService` 绑定。
