## 1. SecNeo 加固链（已验证）

`classes.dex` 仅 `21,820` 字节，只有七个 `com.secneo.apkwrapper` 类：`AP`、`AW`、`CP`、`H$a`、`H`、`a`、`b`。Manifest 的 Application 被替换为 `com.secneo.apkwrapper.AW`，AppComponentFactory 为 `com.secneo.apkwrapper.AP`。原始 Application `com.mc10086.cmcc.base.CmccApplication` 仍以字符串形式出现在加固启动桩。

从 DEX 方法表与字节码调用点确认：

- `AW.attachBaseContext()` 的代码区从 `0x3b18` 开始，调用 `H.a(Landroid/content/pm/ApplicationInfo;)V`。
- `H.<clinit>` 的代码区为 `0x427c`；`const-string` 引用了 `DexHelper`（指令文件偏移 `0x42dc`）及原始 `CmccApplication`（`0x429c`）。
- `H.a(I)I` 的代码区为 `0x4328`；它分别在 `0x435a`、`0x437c`、`0x4420` 引用了 `/proc/self/status`、`TracerPid:` 和 `read tracer`；其字节码还使用 `BufferedReader`、`String.startsWith`、`String.substring`、`String.trim` 和 `Integer.parseInt`。所以加固启动桩具备读取并解析 `TracerPid` 的实际代码，属于反调试相关实现。尚未证明这一方法参与了 DEC 警告，也不能据此推断检测结果。

所带 SO 文件大小：

| 文件 | 字节数 | 静态发现 |
| --- | ---: | --- |
| `libDexHelper.so` | 1,250,586 | ELF ARM64；出现 `JNI_OnLoad`、`/proc/self/maps` 字符串 |
| `libdexjni.so` | 4,467,493 | ELF ARM64；出现 `JNI_OnLoad`、`/proc/self/maps` 字符串 |
| `libdatajar.so` | 158,739,792 | ELF ARM64；包含大规模类名、方法名元数据；没有可直接解出的标准 Dex 文件头 |
| `libdexvmp.so` | 523,584 | ELF ARM64；存在保护/非标准节表布局，`readelf -d` 报告 dynamic section 异常 |

以上文件组合符合 APKiD `SecNeo.C` 的签名：<https://github.com/rednaga/APKiD/blob/master/apkid/rules/apk/packers.yara>。`libdatajar.so` 同样出现 ELF 动态节解析异常；其结构不能按普通包含完整应用函数的 `.so` 直接解释。

## 2. DEC 组件（已验证）

Manifest 中存在：

```text
<activity android:name="com.a.b.c.DECMsgDialog"
          android:exported="false"
          android:theme="0x0103000f" />
```

> 注：`0x0103000f` 是原始二进制主题资源 ID；上述 XML 仅为字段的可读展示。组件名、exported 值都来自 Manifest 直接解码。

`libdatajar.so` 中存在以下原版字节字符串：

| 明文 | 文件偏移 |
| --- | --- |
| `Lcom/a/b/c/DECApp;` | `0x3feb83`、`0x3134768` |
| `Lcom/a/b/c/DeviceEnvironmentCheck;` | `0x3febc3` |
| `getCheckResult` | `0x7ec143e` |

**后续复核（2026-10-22）：** 已恢复 `0x7ec143e` 所在的 Dex 方法表，确认 `getCheckResult` 归属于 `Lcom/alipay/mobile/quinox/resources/BundleResources;`（method_id 10684）。该方法与 `DeviceEnvironmentCheck` 的直接归属关系已排除。原报告该部分是早期阶段的边界说明，详情见 [14 组 Dex 元数据扫描](12.5.5-fourteen-dex-census.md)。

扫描 APK 9,807 个条目的 ASCII/UTF-16LE 明文后：

- `DECMsgDialog`：仅命中 `AndroidManifest.xml`。
- `DeviceEnvironmentCheck`：仅命中 `libdatajar.so`。
- `envc.push`：全 APK 没有明文命中。

没有明文字节只证明它可能被加密、拆分拼接或运行时生成，不代表对应类、文件、功能不存在。日志已独立证明 DEC 弹窗会在运行时真正启动。

## 3. 其他 Root 检测代码的线索（已验证存在，调用关系未验证）

`libdatajar.so` 文件偏移 `0x3b0921f` 含有 `Lcom/mc10086/lib/tools/root/RootBeer;`；相邻区域还含 `FileNative`、`SysHelper` 等类描述符。可以确认 APK 的受保护代码载体中保留这些类的元数据，暂时无法确定哪些具体检查被调用、是否与 DEC 共用判定或是否导致弹窗。

检索 `frida` 时的可见明文命中为英文 `friday` 等普通词语的子串，不能据此认为 APK 包含显式 `frida` 检测字符串；同样也不能据明文搜索否定 native / 加密检测。

## 4. 动态实验与静态发现的边界

- 手机重启、无 Frida 时：日志确认 `DECMsgDialog` 可以正常启动。
- Frida 17.5.2 和 17.24.3 服务端运行时，即使不执行 Attach：复现中国移动主进程的 `SIGSEGV`，最新一轮故障地址 `0x97c`。
- `0x97c` 的原生调用栈无法展开，至今没有被定位到 `libDexHelper.so`、`DeviceEnvironmentCheck` 或具体的 Frida 检测函数。不能宣称已经证实主动反 Frida。
