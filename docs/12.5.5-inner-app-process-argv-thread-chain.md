## 一、`execl` 实际参数布局

内层 ELF 的 `0x5A710` 确定为 `execl@plt` 调用。此前仅识别了 `/system/bin/app_process` 路径，现在可从原版机器码、常量、栈布局及 AArch64 调用约定恢复以下参数：

| 调用位置 | 恢复的参数 | 原版构造证据 |
|---|---|---|
| `x0` | `/system/bin/app_process` | 栈 `sp+0x580`，原版向量加减运算构造 |
| `x1` | `/system/bin/app_process`（argv0） | 与 x0 相同的栈地址 |
| `x2` | `/system/bin` | `/system/`、`bin` 常量拼接；`sp+0x60` |
| `x3` | **`--nice-name=zygote`** | `--nice-n`、`ame=`、运行时解码 `zygote` 拼接；`sp+0x5b0` |
| `x4` | **未知 Java 入口类名** | `0x5A4F4: add x22,x21,#0xe0`；`0x5A708: mov x4,x22`，依赖运行时配置 |
| `x5` | `--write-fd` | `--write-` 与 `fd` 构造；`sp+0xb0` |
| `x6` | **管道写端 FD 的十进制字符串，数值随运行变化** | `0x5A404` 格式化原始管道文件描述符；`0x5A40C` 经 `strdup` 复制，随后从 `sp+0x18` 取得 |
| `x7` | `--flags` | `--fl`、`ag` 和 `s` 构造；`sp+0x98` |
| `[sp]` | `0` | 使用原版 `%d` 格式串与零值生成十进制文本；`sp+0x78` |
| `[sp+8]` | `NULL` | `0x5A70C: stp x21,xzr,[sp]`，作为 `execl` 参数终止符 |

`execl` 调用之前还有原版 `setenv` 调用，设置 `CLASSPATH`，其值是运行时变量。这进一步说明其目的涉及启动另一份 Java 运行时，但**不能单凭静态常量识别具体 Java main 类**。

### 字符表解码的地址陷阱

`JNI_OnLoad` 中 `0x149CC–0x14A18` 有一个对 95 个字节进行循环异或的原版 ARM64 实现。解码目标 ELF **虚拟地址** `0x1240F4`，并用 `0xF4DE5` 的三字节循环表操作。原版 `PT_LOAD` 明确规定数据段存在 **`0x4000` 的文件偏移差**：

- 目标虚拟地址 `0x1240F4` → 原始内层 ELF 文件偏移 `0x1200F4`。
- 解码结果严格等于 ASCII `0x20–0x7E`，完整覆盖 95 个可打印字符。
- 选择 `0x124139` 为基地址，从表中依次读取偏移 `0x15`、`0x14`、`0x02`、`0x0A`、`0x0F`、`0x00`，得到 `zygote`。

这一转换经过原版字节与 ELF Program Header 交叉校验。如果直接把 ELF 虚拟地址当作文件偏移，将读出完全错误的字符串；回归测试专门防止这种地址错误。

**`--nice-name=zygote` 是应用主动构造的参数。** 它本身不能证明实际运行进程获得系统 Zygote 权限，也不能证明设备上哪个 PID 接收了这个参数。

## 二、JNI 初始化至创建进程代码的静态调用关系

此前报告已经确认同一受保护内层 ELF 包含 `JNI_OnLoad`、`fork`、`execl`，但由于 `fork` 的位置远离 `JNI_OnLoad` 的符号范围，无法确定调用者。现在原版机器码提供了新的连接：

| 原版内层 ELF 地址 | 指令与含义 |
|---|---|
| **`0x16990`** | `JNI_OnLoad` 内的直接 `BL 0x1DF7C` |
| **`0x1E3F0 / 0x1E3F4`** | `ADRP/ADD` 形成原生回调函数地址 `0x4E1C8` |
| **`0x1E3F8`** | `STR` 将该地址写入全局表 `0x12B400 + 0x20` |
| **`0x4FFF0 / 0x4FFF4`** | `ADRP/ADD` 构造线程入口函数地址 **`0x59700`** |
| **`0x50004`** | `BL pthread_create@plt`，`x2=0x59700`，`x3=NULL` |
| **`0x5000C–0x50030`** | 再次构造相同线程函数地址并调用 `pthread_create`，属于失败后的重试分支 |
| **`0x59700`** | 独立线程函数入口；`0x59738` 调用 `sleep(2)` |
| **`0x5A3D0`** | 线程函数内 `pipe@plt` |
| **`0x5A418 / 0x5A4C4`** | 线程函数内两次 `fork@plt` |
| **`0x5A710`** | 线程函数内 `execl("/system/bin/app_process", ...)` |

这是目前能够直接从原版机器码恢复的**JNI 初始化 → 注册回调 → 线程函数 → 双重 fork → app_process 启动机制**。其中全局表内的回调何时、由谁读取并调用，尚未得到完整执行路径证明；所以“实际每轮均由这条代码创建 PID 9187/11209”仍需独立运行时证据。

## 三、函数边界：来自原版 `.eh_frame`，已经核验

在原始内层 ELF 的 `.eh_frame`（文件偏移 `0x1063A0`）中读取原生 FDE 的 pcrel 地址编码，得到了四段**独立函数范围**：

| FDE 记录相对位置 | 实际函数范围 | 研究用途 |
|---|---|---|
| `0x788` | `[0x148CC, 0x1703C)` | 真正的 `JNI_OnLoad` 函数 |
| `0x32C8` | `[0x1DF7C, 0x249D0)` | JNI 调用的回调表初始化函数 |
| `0x1CC8` | `[0x4E1C8, 0x50354)` | 含 `pthread_create` 调用点的函数 |
| `0x1FB0` | `[0x59700, 0x5B45C)` | 含 `pipe/fork/execl` 的线程函数 |

该证据进一步解决了反汇编器因符号缺失而使用 `JNI_OnLoad+偏移` 标签的误导。当前双重 fork 函数的边界由真实 unwind 元数据支持，已经独立于函数名称推测。

同时，全量扫描原版 `.text` 的直接 `BL` 指令，**没有找到直接 `BL 0x59700`**；这与该地址通过 `pthread_create` 的函数指针参数传入一致，但不排除还有间接调用路径。

## 四、仍待恢复的环节

1. **回调表调用处**：`JNI_OnLoad` 中已经有进入注册表初始化函数的静态调用；还需要追踪读取全局表中 `0x20` 槽并调用 `0x4E1C8` 的实际执行条件。
2. **Java 主类的实际内容**：`execl` 的 `x4` 来自运行时结构体 `x21+0xe0`，静态文件不能提供该值。设备日志中的 `RuntimeInit` 行也没有明示入口类。
3. **设备事件对应**：两轮独立 `RuntimeInit` 在主进程启动后约 4.75 秒出现，双重 fork 代码内有 `sleep(2)`，这与观察存在时间相关性，不能直接得出运行时执行或 PID 归属证明。
4. **DEC 检测路径**：`DeviceEnvironmentCheck.startCheck()`、触发 `DECMsgDialog` 的判定函数及 Frida SIGSEGV 的具体成因依然未定位。
