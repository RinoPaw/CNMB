- [`audit_inner_spawn_thread.py`](../tools/audit_inner_spawn_thread.py)：`JNI_OnLoad` 调用、全局回调表、`pthread_create` 入口、独立函数边界与 `fork/execl` 路径校验

## 一、`execl` 实际参数布局

内层 ELF 的 `0x5A710` 确定为 `execl@plt` 调用。此前仅识别了 `/system/bin/app_process` 路径，现在可从原版机器码、常量、栈布局及 AArch64 调用约定恢复以下参数：

| 调用位置 | 恢复的参数 | 原版构造证据 |
|---|---|---|
| `x0` | `/system/bin/app_process` | 栈 `sp+0x580`，原版向量加减运算构造 |
| `x1` | `/system/bin/app_process`（argv0） | 与 x0 相同的栈地址 |
| `x2` | `/system/bin` | `/system/`、`bin` 常量拼接；`sp+0x60` |
| `x3` | **`--nice-name=zygote`** | `--nice-n`、`ame=`、运行时解码 `zygote` 拼接；`sp+0x5b0` |
| `x4` | **未知 Java 入口类名** | `0x5A4F4: add x22,x21,#0xe0`；`0x5A708: mov x4,x22`，依赖运行时配置 |
| `x5` | `--write-fd` | `--write-` 与 `fd` 构造；`sp+0xb0` |
| `x6` | **管道写端 FD 的十进制字符串，数值随运行变化** | `0x5A404` 格式化原始管道文件描述符；`0x5A40C` 经 `strdup` 复制，随后从 `sp+0x18` 取得 |
| `x7` | `--flags` | `--fl`、`ag` 和 `s` 构造；`sp+0x98` |
| `[sp]` | `0` | 使用原版 `%d` 格式串与零值生成十进制文本；`sp+0x78` |
| `[sp+8]` | `NULL` | `0x5A70C: stp x21,xzr,[sp]`，作为 `execl` 参数终止符 |

`execl` 调用之前还有原版 `setenv` 调用，设置 `CLASSPATH`，其值是运行时变量。这进一步说明其目的涉及启动另一份 Java 运行时，但**不能单凭静态常量识别具体 Java main 类**。

### 字符表解码的地址陷阱

`JNI_OnLoad` 中 `0x149CC–0x14A18` 有一个对 95 个字节进行循环异或的原版 ARM64 实现。解码目标 ELF **虚拟地址** `0x1240F4`，并用 `0xF4DE5` 的三字节循环表操作。原版 `PT_LOAD` 明确规定数据段存在 **`0x4000` 的文件偏移差**：

- 目标虚拟地址 `0x1240F4` → 原始内层 ELF 文件偏移 `0x1200F4`。
- 解码结果严格等于 ASCII `0x20–0x7E`，完整覆盖 95 个可打印字符。
- 选择 `0x124139` 为基地址，从表中依次读取偏移 `0x15`、`0x14`、`0x02`、`0x0A`、`0x0F`、`0x00`，得到 `zygote`。

这一转换经过原版字节与 ELF Program Header 交叉校验。如果直接把 ELF 虚拟地址当作文件偏移，将读出完全错误的字符串；回归测试专门防止这种地址错误。

**`--nice-name=zygote` 是应用主动构造的参数。** 它本身不能证明实际运行进程获得系统 Zygote 权限，也不能证明设备上哪个 PID 接收了这个参数。

## 二、JNI 初始化至创建进程代码的静态调用关系

此前报告已经确认同一受保护内层 ELF 包含 `JNI_OnLoad`、`fork`、`execl`，但由于 `fork` 的位置远离 `JNI_OnLoad` 的符号范围，无法确定调用者。现在原版机器码提供了新的连接：

| 原版内层 ELF 地址 | 指令与含义 |
|---|---|
| **`0x16990`** | `JNI_OnLoad` 内的直接 `BL 0x1DF7C` |
| **`0x1E3F0 / 0x1E3F4`** | `ADRP/ADD` 形成原生回调函数地址 `0x4E1C8` |
| **`0x1E3F8`** | `STR` 将该地址写入全局表 `0x12B400 + 0x20` |
| **`0x4FFF0 / 0x4FFF4`** | `ADRP/ADD` 构造线程入口函数地址 **`0x59700`** |
| **`0x50004`** | `BL pthread_create@plt`，`x2=0x59700`，`x3=NULL` |
| **`0x5000C–0x50030`** | 再次构造相同线程函数地址并调用 `pthread_create`，属于失败后的重试分支 |
| **`0x59700`** | 独立线程函数入口；`0x59738` 调用 `sleep(2)` |
| **`0x5A3D0`** | 线程函数内 `pipe@plt` |
| **`0x5A418 / 0x5A4C4`** | 线程函数内两次 `fork@plt` |
| **`0x5A710`** | 线程函数内 `execl("/system/bin/app_process", ...)` |

这是目前能够直接从原版机器码恢复的**JNI 初始化 → 注册回调 → 线程函数 → 双重 fork → app_process 启动机制**。其中全局表内的回调何时、由谁读取并调用，尚未得到完整执行路径证明；所以“实际每轮均由这条代码创建 PID 9187/11209”仍需独立运行时证据。

## 三、函数边界：来自原版 `.eh_frame`，已经核验

在原始内层 ELF 的 `.eh_frame`（文件偏移 `0x1063A0`）中读取原生 FDE 的 pcrel 地址编码，得到了四段**独立函数范围**：

| FDE 记录相对位置 | 实际函数范围 | 研究用途 |
|---|---|---|
| `0x788` | `[0x148CC, 0x1703C)` | 真正的 `JNI_OnLoad` 函数 |
| `0x32C8` | `[0x1DF7C, 0x249D0)` | JNI 调用的回调表初始化函数 |
| `0x1CC8` | `[0x4E1C8, 0x50354)` | 含 `pthread_create` 调用点的函数 |
| `0x1FB0` | `[0x59700, 0x5B45C)` | 含 `pipe/fork/execl` 的线程函数 |

该证据进一步解决了反汇编器因符号缺失而使用 `JNI_OnLoad+偏移` 标签的误导。当前双重 fork 函数的边界由真实 unwind 元数据支持，已经独立于函数名称推测。

同时，全量扫描原版 `.text` 的直接 `BL` 指令，**没有找到直接 `BL 0x59700`**；这与该地址通过 `pthread_create` 的函数指针参数传入一致，但不排除还有间接调用路径。

## 回调调用条件已恢复：初始化线程中的 0x04 标志位

对上面的注册表继续反查，原版还包含另一层 `pthread_create`：

1. `JNI_OnLoad:0x16990` 调用的 `0x1DF7C` 在 `0x1E4F4` 创建线程 **`0x4B3BC`**；`0x1E520` 是该线程创建失败时的重试调用，两次的线程上下文参数均为 `x20`。
2. 初始化函数将配置标志字节写入 `context+0x08`（`0x1E458: strb w19,[x0,#8]`）。线程入口 `0x4B3BC` 在 `0x4B3F0` 用 `ldrb w20,[x19,#8]` 读取同一个标志。
3. 线程在 `0x4B480–0x4B494` 定位全局表 `0x12B400`，执行 `x8=x20 & 4`，随后 `ldr x8,[table,x8,lsl #3]` 和 `blr x8`。因此，当 **bit `0x04` 为 1** 时，实际读取的是 `table+0x20`，恰好是 `0x1E3F8` 写入的函数 `0x4E1C8`。
4. 该函数在 `0x50004` 使用 `pthread_create` 启动线程 `0x59700`；后者位于独立 unwind FDE `[0x59700,0x5B45C)`，内部执行双重 `fork` 和 `execl`。

继续沿 bit `0x04` 反查：初始化函数在 `0x1E014` 读取运行时配置结构体 **`+0x4A` 处的字节**，在 `0x1E080` 将该字节与 0 比较，`0x1E084` 选择基础标志值或 `基础值 | 5`；基础值经检查均未设置 `0x04`，后续 `OR 0x40` 也不影响这一位。故对已验证的**正常初始化分支**，结论是：

```text
runtime_config[0x4A] != 0
    → flags |= 0x04
    → dispatcher thread uses callback_table[0x20]
    → callback 0x4E1C8
    → pthread_create(..., 0x59700, ...)
    → pipe, fork, fork, execl(app_process, ...)
```

该分支具有原版 ELF 中实际机器指令、调用目标、函数地址和 `.eh_frame` 边界的直接支持。作为跨层证据，目前可以确定 **`JNI_OnLoad` 已经通过可执行的条件分发路径连接到原生 app_process 创建函数**；但配置 `+0x4A` 的具体语义、设备当次值、特殊错误分支行为以及观察到的 PID 一一归属仍未确定。

`.eh_frame` 还确认了分发线程函数范围 **`[0x4B3BC,0x4B768)`**（FDE `0x1C18`）。没有任何理由继续把 `0x4B3BC` 或 `0x59700` 归入 `JNI_OnLoad` 的单一函数体。

## 2026-10-23 进一步验证：原版内置配置里的开关值为 true

沿前述 `runtime_config[0x4A]` 字节继续向上追踪，已经恢复其**原版内置序列化配置中的对应字段值**。证据链全部来自解码后且 SHA-256 匹配的原版内层 `libDexHelper.so`：

1. `JNI_OnLoad:0x14A54–0x14A58` 定位配置写入目标 `x22=0x12A440`；`0x14B08` 构造内置配置数据地址 `0x12415B`，并在 `0x14B28` 调用 `0x8569C` 初始化序列化读取器。
2. `0x8569C` 保存数据地址和函数 `0x2870C`。该函数在 `0x28758` 与 `0x2878C–0x28798` 使用 **`0xAC` XOR** 解码字节；得到的是标准 MessagePack 的布尔值、无符号整数及二进制块序列。
3. 按照 `0x14B34–0x14C2C` 15 项解析调用的真实顺序，前 14 项的类型及长度均可匹配；第 15 项恰好由 `0x14C24` 将地址设置为 `x22+0x4A`，`0x14C2C` 调用 `0x85C9C`，最终在 `0x85CE4` 写入解析后的布尔值。
4. 该字段位于内置数据流相对字节偏移 **63**（内层 ELF 数据 VA `0x12415B`，实际文件偏移 `0x12015B`）。文件原始编码字节经 XOR 解码为 **`0xC3`**，在 MessagePack 中表示 **`true`**。

因此可以确定：**原版内置配置的第 15 项会写入静态配置结构体的 `+0x4A` 字段，值为真。** 同一个内层 ELF 的 `0x1E014` 通过独立的运行时配置指针读取 `+0x4A`，从正常分支确定 `0x04` 回调位的选择规则。

目前尚有一项**必须保留的边界**：`JNI_OnLoad` 的静态序列化目标位于 `0x12A440`，后续初始化器所用的运行时指针槽则位于 `0x128000`（由 `0x123DC0` 的相对重定位得到）。原版代码虽具有相同字段偏移，但仍需证明两份存储之间的实际复制/引用关系，以及运行期间是否修改 `+0x4A`。因此尚不能宣称“设备上每轮分发线程实际都读到了 true”，更不能把这个布尔字段直接命名为 Root 或 DEC 标志。

序列化配置中另有 `com/secneo/apkwrapper/AW`、`com/secneo/apkwrapper/H`、`com/fort/andjni/JniLib0` 等类路径；它们只是当前原始配置中出现的**入口候选**，尚未证明被 `execl` 的 `x4` 参数选中。

[只读验证器](../tools/audit_inner_spawn_config.py) 使用原始 APK/内层 ELF 哈希校验、ELF 虚拟地址转换、15 项标准库 MessagePack 前缀解析及原版 ARM64 机器指令核验；对应 [合成数据测试](../tests/test_audit_inner_spawn_config.py)。不导出密钥、原始配置块或恢复的商业二进制。

## 2026-10-23 更新：原版 Java 入口类的默认值与运行时覆盖

继续沿 `execl:0x5A708` 的 `x4` 数据源向前追踪，已经定位默认 Java 主类的实际构造路径：

- `JNI_OnLoad` 中的 `0x152A8` 直接调用 `0x1703C`。该函数在 `0x17078–0x1708C` 为运行时对象分配 **`0x680` 字节堆内存**，并将指针保存至全局位置 `0x12A418`。
- 在 `0x17328–0x173E8`，23 次原版 ARM64 `LDRB/STRB` 指令从此前解码的 95 字节可打印 ASCII 表中取字符，构造 `com/secneo/apkwrapper/H\0`。这是**原版机器指令直接证明的默认 Java 类路径**，规范点分形式为 `com.secneo.apkwrapper.H`。
- `0x173F0` 检查另一运行时配置结构的 `+0x200` 字段（候选覆盖串长度）；`0x173F8` 可取得 `+0x208` 处保存的覆盖字符串指针。没有有效覆盖数据时，`0x1740C` 选择上述栈上的默认字符串。
- `0x17438–0x17484` 将最终选中的类路径拷贝至**分配对象的 `+0xE0` 字段**并以零结尾。创建子进程的工作线程在 `0x5A040/0x5A410` 读取全局 `0x12A418` 指针，`0x5A4F4` 取 `+0xE0`，`0x5A708` 把该地址设置到 **`execl` 的 `x4` 参数**。

与此前“Java 主类参数来自未知动态指针”的情况相比，现已确定其**原版默认值为 `com.secneo.apkwrapper.H`，并证明两处使用同一个堆对象指针和相同字段偏移**。

当前依然需要注意：运行时结构体可以提供覆盖主类字符串。此前日志 `RuntimeInit` 没有打印明确的 main 类名，因此尚不能断言设备上实际执行的主类必然就是这个默认值，也不能自动将其等同于 `DeviceEnvironmentCheck.startCheck()` 的实现者。

复核代码见 [`audit_inner_java_entry.py`](../tools/audit_inner_java_entry.py) 和 [合成测试](../tests/test_audit_inner_java_entry.py)。验证过程逐一检查原版字符读取、栈存储位置、堆对象指针、`+0xE0` 拷贝及 `execl(x4)` 参数传递，不上传任何恢复出的商业 SO。

## 四、仍待恢复的环节

1. **回调开关的运行时值**：已找到分发线程和 `runtime_config[0x4A] != 0` 的条件路径，但尚未恢复此配置字段的产生代码、含义及当次启动的实际取值。
2. **Java 主类的实际内容**：`execl` 的 `x4` 来自运行时结构体 `x21+0xe0`，静态文件不能提供该值。设备日志中的 `RuntimeInit` 行也没有明示入口类。
3. **设备事件对应**：两轮独立 `RuntimeInit` 在主进程启动后约 4.75 秒出现，双重 fork 代码内有 `sleep(2)`，这与观察存在时间相关性，不能直接得出运行时执行或 PID 归属证明。
4. **DEC 检测路径**：`DeviceEnvironmentCheck.startCheck()`、触发 `DECMsgDialog` 的判定函数及 Frida SIGSEGV 的具体成因依然未定位。
