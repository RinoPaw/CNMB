# 中国移动 12.5.5：SecNeo Messenger Service 绑定条件与 IsoService 来源

核验日期：2026-10-24。唯一原始样本为中国移动 12.5.5 base APK（SHA-256 `6282d2cf05f76f37a60fff322bcf0d6f1d876829e5c9c4eae5cdd93b7a972a83`）；原版 `classes.dex` SHA-256 `6abbe8c56cc92a5d33cc12b2fdfda9a487325382e62b321359db65c98a27ca17`，恢复的内层 `libDexHelper.so` SHA-256 `b0d42eb0d86a7fdd3c4e5669c46376d0d4c041da5adb3f5d0e3ccbe9f369ef54`。所有证据来自这些原始字节以及 Manifest 的 Binary XML 结构；没有推测其他 SecNeo 版本的实现。

本篇续接 [Messenger → H.he(int) 静态路径](12.5.5-secneo-h-messenger-native-route.md)。研究问题：默认启动是否一定绑定远端服务、远端类名从何而来，以及收到回复后如何清理连接。

## 1. Java 可达入口与 PC_FLAG 默认值

原版 `H.<clinit>` 的 DEX 指令：

- `0x42EC`：`const-string`，string_id 14 为字符串 **`255`**。
- `0x42F0`：`sput-object`，field_id 11 为 `H.PC_FLAG`。
- `0x42FE–0x4308`：创建 `com.secneo.apkwrapper.b`，赋给 `H.sConnection`。

原版 `AW.onCreate` 包含对 `H.callSW(Context)` 和 `H.callBS(Context)` 的直接 invoke。两个 H 包装方法分别读取 `PC_FLAG`，调用 `Integer.parseInt`，再于 `0x4C42` 调用 `H.sw(Context,int)`、`0x4BE6` 调用 `H.bs(Context,int)`。这些方法均是原始 DEX 中的 Native 声明。

内层 ELF 的另一张 `RegisterNatives` 表在 `0x154A4` 配置四个方法，`0x155E4/0x155E8` 执行注册；从原版表项 ADRP/ADD 和 JVM 方法签名验证：

| Java Native 方法 | 原生地址 | 原版分支或用途 |
| --- | --- | --- |
| `sw(Context,int):void` | `0x2C440` | `0x2C46C` 检查参数 bit0 |
| `bs(Context,int):Object` | `0x2C8D8` | `0x2C90C` 检查参数 bit1 |
| `is(int):boolean` | `0x2D158` | 另一个注册的原生接口；业务路径未追完 |
| `us(Context):void` | `0x2D178` | `Context.unbindService` 调用链 |

原版 `sw` 的指令为 `0x2C46C: tbnz w3,#0,0x2C8AC`；`bs` 为 `0x2C90C: tbnz w3,#1,0x2C930`。两处目标均在函数的提前返回分支。**初始 PC_FLAG=255=0xFF，因此两位都是 1：在该初始配置和参数未改写的条件下，两个原生函数都提前返回。**

对原版基础 `classes.dex` 的 **65 个代码项**进行 16 位对齐的字段指令候选扫描，field_id 11（`H.PC_FLAG`）只有三处命中：`0x42F0` 在 `H.<clinit>` 写入，`0x4BDA` 在 `H.callBS` 读取，`0x4C36` 在 `H.callSW` 读取。这三处的实际 Dalvik 机器字均已逐条核对。**基础 DEX 中只确认到一次直接字段写入**；该扫描覆盖不了反射、JNI 写字段、其他运行时加载的 DEX，也未进行通用 DEX 全指令解码。

本结论仅约束**原版 Java 初始化的默认字符串**和 Native 入口的静态位测试；仍不能排除后续通过反射、JNI 或其他运行时参数改变 `PC_FLAG` 或直接调用原生函数的其他路径。H.java 含有绑定代码也不意味着默认每次都触发绑定。

## 2. 允许通过 bit1 守卫时如何构造远端服务

`bs` 的守卫允许进入后，原版 ARM64/JNI 调用序列包含：

1. `0x2CB84` 使用 JNIEnv 的 `FindClass`，取得 `android/content/Intent`；查找它的 `<init>(Context,Class)` 构造器。
2. `0x2CC5C..0x2CCD4` 的十三条 `LDRB` 从原始 JNI 可打印字符表（此处基址为表 `+5`）恢复格式串 **`%s/IsoService`**。
3. `0x2CC68` 从运行时对象传入 `+0x40` 字段作为命名空间参数，`0x2CCE0` 调用内部格式化函数；后续代码还处理类名中的点与斜杠，随后以 `FindClass` 获取类引用。**具体包名前缀是运行时数据，静态格式串不足以确认完整 FQCN**。
4. `0x2CD84` 经 JNI `NewObjectV` 包装调用构造目标 `Intent(Context,Class)`。
5. `0x2CE78..0x2CEC8` 的独立 `LDRB` 还原 Java 虚方法名 **`bindService`**，再通过 `GetMethodID` 查找 `Context.bindService(Intent,ServiceConnection,int)`。
6. `0x2D008..0x2D094` 原版逐字节生成 **`BIND_AUTO_CREATE`**，调用 `GetStaticFieldID` 和 `GetStaticIntField` 获取实际 Java 静态常数，传给 `bindService`。
7. `0x2D0EC` 调用包装函数 `0x2A44C`，其中 `0x2A4B8` 的 JNI 虚表项 `+0x130` 为 `CallBooleanMethodV`，与 `Context.bindService` 返回 boolean 一致。

这是一条有明确守卫的 **`Context.bindService(Intent(Context, IsoService-class), H.sConnection, Context.BIND_AUTO_CREATE)`** JNI 静态调用链。没有足够证据宣称运行中注册的 `IsoService` 类、服务实例或绑定成功。特别不能把名字相近的 `IsolatedService` 等其他 SDK 服务直接当成 `IsoService`。

## 3. 原版回复收到后会解绑

原始基础 DEX 中，`H$a.handleMessage` 对 `Message.what=1000` 的分支：

- 如果 `H.sApp` 非空，先取 `Application.getApplicationContext()`，在 `0x424E` 直接调用 `H.us(Context)`。
- 之后 `0x4254` 从 **`Message.arg2`** 取整数，`0x4258` 调用 `H.c(int)`，最终进入 Native `H.he(int)`。

在原生 `0x2D178` 的实现中，字符表构造出 **`unbindService`**，以 `GetStaticObjectField` 取得 H 的 `sConnection`，并在 `0x2D474` 调用包装函数 `0x2A3B0`；后者通过 JNIEnv 虚表 `+0x1F0` 执行 `CallVoidMethodV`。由此可恢复 **`Context.unbindService(H.sConnection)`** 的静态路径。成功解绑需要运行时有效的已绑定 ServiceConnection；原始静态代码无法证明这一条件在某轮手机上成立。

收到的 `Message.arg2` 值仍没有原版服务端赋值代码或本机逐条 Messenger 日志来证明；发送端发出的请求则明确把 `Process.myPid()` 放入 **`Message.arg1`**。不能把这两个字段混为同一来源。

## 4. Manifest 中缺少 IsoService 的声明

直接解析固定哈希 APK 的 `AndroidManifest.xml` Binary XML：读取 `START_ELEMENT` 的 `service` 标签及其 `android:name`，共确认 **78 个 service 条目**。**没有一个以 `IsoService` 结尾**，亦未发现精确 `com.secneo.apkwrapper.IsoService`。原版的 `com.ijm.detect.drisk.IsolatedService` 具有不同完整名称，不能混淆。

由于前述 Java 原生桥接通过显式 `Intent(Context,Class)` 指向运行时构造的类，且当前基础 APK 的 Manifest 无对应组件声明，因此**不能宣称该原版基础包必然完成绑定**。仍有动态组件/拆分安装包或运行时替换等未验证情况；应先核查实际发起绑定的证据和服务端 class，再追 `what=1000` 的回复 `arg2`。

## 5. 研究结论、工具与边界

本轮新增 [只读原版服务生命周期审计](../tools/audit_inner_h_service_lifecycle.py) 和 [合成回归测试](../tests/test_audit_inner_h_service_lifecycle.py)。审计程序固定 APK、基础 DEX 和内层 ELF 哈希；检查 DEX `PC_FLAG=255`/invoke 字节码、另一张四项 JNI Native 注册表、原生 bit0/bit1 提前返回分支、字符表构造出的 `IsoService` / `bindService` / `unbindService` / `BIND_AUTO_CREATE`，解析 Binary Manifest 以逐项统计服务声明。只输出脱敏的结构结论，不输出 APK、SO、完整 Manifest 路径或用户私有文件。

~~~powershell
python .\tools\audit_inner_h_service_lifecycle.py .\path\to\original-base.apk
~~~

**已证明：** 原始代码包含 IPC 服务绑定和解绑的确切 JNI 调用，默认 `PC_FLAG=255` 会命中两个提前返回位，静态目标名格式是 `%s/IsoService`；原版 base Manifest 没有同名 Service。

**仍未证明：** 实际运行时 PC_FLAG 值，远端服务是否可成功绑定，任何真实回复消息中的 `arg2` 值，`H.he(int)` 是否被执行及它与 DECMsgDialog 或 `SIGSEGV 0x978/0x97c` 的直接因果关联。这条静态路线揭示了先前工作中“存在完整 Handler 发送与回复代码就必定发生 Service 往返”的风险。
