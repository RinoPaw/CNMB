# 12.5.5：完整 SO 中的 14 组可恢复 Dex 元数据与 `getCheckResult` 归属

日期：2026-10-22。样本为中国移动 12.5.5 原始 `lib/arm64-v8a/libdatajar.so`；SHA-256 为 `8b0777aeeedb1d95041fb8b5a900735d607505f802255227a82c83225d8bbf81`。本文所有偏移均为**原始 SO 的文件偏移**。

这次以先前恢复的 3 组 Dex 为起点，对 **158,739,792 B** SO 中的 32-bit 小端整数序列开展连续索引扫描。对每组候选验证实际字符串的 ULEB128 长度、NUL 终止与连续偏移，再顺序推导 `type_ids`、`proto_ids`、`field_ids`、`method_ids` 和 `class_defs`。**这是 Dex 元数据片段取证；未恢复完整 Dex Header，也未解密所有代码。**

## DEC 类定义完整性

经过全部 14 组表检查，只发现以下属于 `Lcom/a/b/c/` 前缀的类型：

| 所在片段 | 类型 ID | 原始类描述符 | 类定义 |
|---|---:|---|---|
| `0x2500c` | 17417 | `Lcom/a/b/c/DECApp$1;` | **存在** |
| `0x2500c` | 17418 | `Lcom/a/b/c/DECApp;` | **存在** |
| `0x2500c` | 17419 | `Lcom/a/b/c/DECLog;` | 只有引用 |
| `0x2500c` | 17420 | `Lcom/a/b/c/DECRunning;` | 只有引用 |
| `0x2500c` | 17421 | `Lcom/a/b/c/DeviceEnvironmentCheck;` | **只有引用** |
| `0x2f2e00c` | 781 | `Lcom/a/b/c/DECApp;` | 只有引用 |

整份 `libdatajar.so` 中，`Lcom/a/b/c/DeviceEnvironmentCheck;` 明文字节序列只出现 **1 次**（字符串内容起始偏移 `0x3febc3`）。

因此，在这 **14 个可恢复的类定义表**中，已经确认没有 `DeviceEnvironmentCheck` 的完整实现。其实际方法体可能来自尚未恢复的加固内容、其他载体或者运行时解密加载；**目前尚未证明具体储存位置及解密方式**。

`DECMsgDialog` 的注册入口可由原版 Manifest 单独证明，但这 14 个片段中没有相应明文类定义。

## 纠正：`getCheckResult` 的归属已经确定

之前发现的字符串 `getCheckResult` 位于 SO `0x7ec143e`，此前曾怀疑可能关联 `DeviceEnvironmentCheck`。本次从 **`0x7b8d00c`** 片段恢复了完整方法引用索引：

- `getCheckResult` 的字符串 ID：**50767**
- `method_id`：**10684**
- 所属类型 ID：**2113**
- 方法所有者：**`Lcom/alipay/mobile/quinox/resources/BundleResources;`**
- 所有者的 `class_def`：**存在**

故该特定 `getCheckResult` 字符串及方法引用可以排除作为 `DeviceEnvironmentCheck.getCheckResult` 的证据；尚未证明支付宝组件与 DEC 的任何调用关系。

## ELF 层的补充观察

`libdatajar.so` 是 ELF64/AArch64 共享对象。其一个大型可写 `LOAD` 段从文件偏移 `0x3db0` 起，`FileSiz=0x975d25c`；同时存在很小的两个可执行 `LOAD` 段（`0x790` 与 `0xa50` 字节）。这与它作为大型数据/代码载体的功能相符。但 ELF 布局自身没有证明 `startCheck` 的具体解密位置或运行时入口。
