# 中国移动 12.5.5：恢复双重包装的内层 ELF，定位 fork / execl

核验日期：2026-10-23。唯一数据源为原版中国移动 12.5.5 APK（SHA-256 `6282d2cf05f76f37a60fff322bcf0d6f1d876829e5c9c4eae5cdd93b7a972a83`）。工具 [`tools/audit_nested_elf.py`](../tools/audit_nested_elf.py) 对两个指定的外层 SO 严格验哈希，在内存中恢复受保护的内层 ELF，检查完整映像哈希、Program Header、符号表与 AArch64 调用指令。工具只输出元数据与脱敏路径；原版与解码后的二进制均不入库。

## 1. 恢复原理：64 字节 RC4 头部 + 主体字节异或层

前期已证明 [`libDexHelper.so:0x4780` 的外层 ELF 构造函数](12.5.5-dexhelper-plt-maps-loader.md) 寻找自身 ELF 映射，并使用 `open/pread/mmap/mprotect` 自行装载原生映像。继续解析其本地 `0x3184` 函数：

- `0x32bc–0x32cc` 初始化长 256 的字节置换表（`S[i]=i`）；
- `0x32e4–0x332c` 根据原版 16 字节参数进行 RC4 key scheduling；
- `0x3340–0x33c4` 实现流位置跳过、交换与 XOR 输出（RC4 PRGA）；
- 加载函数从外层 SO 的固定元数据读出内层数据起始/结束偏移，在该结束偏移处读取 16 字节 RC4 参数及后续单字节主体掩码；此类参数始终从用户持有的原版文件读出，**未写入本报告或工具源码**。

通过原版数据验证，64 字节 RC4 解码得到完整有效的 ELF64 头部，随后内层主体使用尾部单字节掩码复原。分别对**完整结果**校验 SHA-256 和全部 ELF Program Header / Section Header 边界：

| 原版外层 SO | 内层加密起点 | 内层 ELF 大小 | 程序头 / 节头 |
|---|---:|---:|---:|
| `libDexHelper.so` | `0x8000` | **1,196,605 B** | 8 / 26 |
| `libdexjni.so` | `0x4000` | **4,438,032 B** | 6 / 20 |

解码结果都为 AArch64 ELF64 `ET_DYN`，其可执行、可写和 `PT_DYNAMIC` 映射区域完整且没有越界。固定的恢复产物哈希保存在验证工具中用于回归，但不输出或发布原始恢复后的 `.so` 文件。

这解释了为何原始文件的动态符号表存在空槽、为什么外层只有 `JNI_OnLoad` 明文字串而缺少该符号导出：**原始外层 SO 内部另有真实 ELF 映像，需要先恢复才能检查其导入/导出与代码。**

## 2. 内层 ELF 中出现真实 `JNI_OnLoad` 导出

通过恢复出的节头和 `SHT_DYNSYM / SHT_SYMTAB`，独立校验：

| 内层 SO | `JNI_OnLoad` ELF VA | 符号声明长度 | 声明结束地址 |
|---|---:|---:|---:|
| `libDexHelper.so` | `0x148CC` | **10,096 B** | `0x1703C` |
| `libdexjni.so` | `0x2EAC` | **148 B** | `0x2F40` |

外层 `DT_HASH` 的全零桶/链表与**内层恢复出的动态符号表**属于不同映像，不可混用。这里已得到直接的文件结构证据，说明原版包含可见的内层 JNI 入口，但仅凭文件不能证明设备当次运行是否调用或恢复了特定内层函数。

## 3. 找到 `fork` 与 `execl` 的真实原生调用

`libDexHelper.so` **内层 ELF** 明确导入 `fork@LIBC` 和 `execl@LIBC`，对应的 PLT 位置分别是 `0xF200`、`0xF7F0`。检查原始 AArch64 `BL` 目标：

- `fork@plt` 在 `0x1B440`、`0x1E610`、`0x1E738`、**`0x5A418`**、**`0x5A4C4`**、`0x602AC`、`0x60C04` 均有直接调用。
- **`0x5A710`** 调用 `execl@plt`。
- `0x5A3D0` 调用 `pipe@plt`；`0x5A418` 第一次 `fork`，父进程分支有 `0x5A454 → waitpid@plt`，子进程分支从 `0x5A4C4` 再次 `fork` 并在孙进程执行后续 `execl`。
- 孙进程内可见 `setenv`、直接 `svc`、进程清理分支等，尚未完成每个参数及状态条件的完整 CFG 恢复。

尤其 `0x5A538–0x5A654` 使用原版向量字节逐字节加法、后续六字节减法等指令，最终在栈上构造出 `/system/bin/app_process\0`；`0x5A6F0` 将其地址送入参数寄存器，`0x5A710` 通过 `execl` 启动该路径。可复核工具直接实现并逐字节验证这套解码，避免靠字符串猜测启动目标。

这与两轮 ADB 实测里具有相同 Java `RuntimeInit` 日志特征、并在首次采样时 PPID=1 的临时进程，形成**明确的机制级关联线索**。但设备上尚未捕获到本次 `execl` 的返回值、启动参数以及具体调用者，所以目前不能把该原生函数与 PID 9187 或 11209 做一对一证明。

## 4. 一项必须纠正的函数归属错误

反汇编工具对缺少符号名的代码可能持续使用前面最近的 `JNI_OnLoad+offset` 标签。**不能据此把整个 ELF 后部代码都当作 `JNI_OnLoad` 函数体**。

恢复后的 `JNI_OnLoad` 静态符号范围为 `[0x148CC,0x1703C)`；双重 `fork` 与 `execl` 位于 `0x5A418–0x5A710`，明显不在该范围内。当前可以说：

1. 内层 `libDexHelper.so` 中存在真实 `JNI_OnLoad` 导出。
2. 同一个内层 SO 中存在 **已由原版 `BL` 指令证实**的双重 `fork`、`waitpid`、`execl("/system/bin/app_process", …)` 路径。
3. **连接 JNI 入口或应用启动方法与该进程创建分支的可达调用链还没有恢复**，完整 Java 入口类参数也尚未解码。
4. 与 `DeviceEnvironmentCheck.startCheck()`、`DECRunning`、DEC 弹窗判定条件及 Frida 引发的崩溃之间仍没有直接归因证据。

此次研究发现了能实际创建辅助 `app_process` 的原版 native 代码，远强于此前仅凭进程时间间隔猜测或只看外层被擦除符号表。下一阶段应进一步还原 `execl` 的全部 argv，随后分析其 C++ / JNI 调用者，与设备 PPID / RuntimeInit 证据严格对应。

## 5. 离线复核

```powershell
python .\tools\audit_nested_elf.py .\path\to\original-base.apk
# 或将相同 SHA-256 的原始诊断 ZIP 作为参数
```

工具仅输出嵌套 ELF 哈希、边界、JNI 符号、`fork/execl` 的 `BL` 调用点、构造的 `app_process` 路径及已知证据边界；**不生成或写出恢复的内层商业二进制**。

## 2026-10-23 更新：JNI 上层调用与完整 argv 已恢复

前述“尚缺 JNI 入口到进程创建代码的联系”如今已有部分原版静态证据支持：`JNI_OnLoad` 的 `0x16990` 直接调用 `0x1DF7C`，后者在 `0x1E3F0–0x1E3F8` 将 `0x4E1C8` 写入全局回调表；`0x4E1C8` 内部的 `0x4FFF0` 和 `0x5000C` 把 `0x59700` 交给 `pthread_create`，线程函数在 `0x5A418`、`0x5A4C4` 两次 fork，并在 `0x5A710` 调用 execl。真实 `.eh_frame` 证实了 JNI、回调注册函数、线程启动函数和 fork 工作函数的独立边界。

从真实 ELF Program Header 翻译 `.data` 虚拟地址并解密 95 字节字符表后，恢复出 `execl` 的 `/system/bin`、`--nice-name=zygote`、`--write-fd`、`--flags` 和 `0` 参数；Java 入口类由运行时指针 `x21+0xe0` 提供，尚未确认。详见 [完整 argv 和调用链专项研究](12.5.5-inner-app-process-argv-thread-chain.md)。

这些新增证据证明了静态 JNI 初始化及回调注册的联系，**仍缺回调表槽的实际调用条件与设备 PID 的精确执行归属**。因此不能宣布已定位 `DeviceEnvironmentCheck.startCheck()` 或 DEC 检测策略。
