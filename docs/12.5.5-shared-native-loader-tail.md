# 12.5.5：十份 ARM64 库共用的 2,640 字节原生装载辅助段

日期：2026-10-22。本报告只使用 SHA-256 固定的**原版**中国移动 12.5.5 APK（`6282d2cf05f76f37a60fff322bcf0d6f1d876829e5c9c4eae5cdd93b7a972a83`）。没有上传商业 APK、SO 和任何运行日志。文件偏移与 ELF 虚拟地址严格区分。

## 一、原版 191 份 arm64 SO 的全量字符串/指令交叉验证

此前 [进程与系统调用审计](12.5.5-native-and-dalvik-process-surface.md) 发现 `libdexvmp.so` 共 34 个 `svc` 编码候选、`libdatajar.so` 共 9 个。继续解码发现二者都包含一个独立的、**2,640 B（`0xa50`）长的可执行 `PT_LOAD`**，并拥有相同的指令结构。

以原始 `libdexvmp.so` 中偏移 `0x7f078` 的尾部代码为基准，用其相对范围 **`[0x20,0xa25)` 共 2,565 B** 作为精确匹配序列，扫描 APK 内全部 **191** 份 `lib/arm64-v8a/*.so` 文件，找到 **10 份**：

| ARM64 库 | 共享尾段起始 SO 文件偏移 | PT_LOAD 虚拟地址 | 与 libdexvmp 的整段字节差异 |
|---|---:|---:|---:|
| `libAlipayBitmapNative.so` | `0x3078` | `0x13078` | 18 B |
| `libdatabase_sqlcrypto.so` | `0x1f2078` | `0x203078` | 23 B |
| `libdatajar.so` | `0x9762078` | `0x9766078` | 26 B |
| `libdexvmp.so` | `0x7f078` | `0x83078` | 0 B |
| `libentryexpro.so` | `0x2c078` | `0x3c078` | 21 B |
| `libijkrecorder.so` | `0xe078` | `0x1f078` | 23 B |
| `libijksdl.so` | `0x76078` | `0x86078` | 23 B |
| `libmmkv.so` | `0x76078` | `0x77078` | 26 B |
| `libv8worker-native.so` | `0xc078` | `0x1c078` | 22 B |
| `libyewu.so` | `0x34078` | `0x56078` | 21 B |

每个命中都经过完整 2,640 B 的尾段取出、相对偏移核心字节校验、原版 ELF64/AArch64 `e_machine=183` 及可执行 `PT_LOAD` 区间核对。核心完全相同，前后少量字节不同，主要属于头部地址与尾部参数区域；**不能把整段都误称为每份 SO 字节完全一致**。

保护段中出现完整原版 ASCII 字串 `__b_a_n_g_c_l_e__check1234567_`（相对偏移 `0x550`）及 `/proc/self/maps`（相对偏移 `0x9f4`）。前者是有力的保护方案签名线索；**仅凭签名还没有证明打包服务商、具体加固版本或者与 SecNeo/DEC 之间的组织关系**。

## 二、九个直接系统调用：号码已由机器指令验证

每份共享尾段都有**相同的九处** `mov x8,#number; svc #0; ret` 指令链。使用 `movz` 立即数和 `svc`、`ret` 机器码断言，结果如下：

| 相对尾段偏移（`svc`） | AArch64 Linux syscall 号 | 作用 |
|---|---:|---|
| `0x100` | 64 | `write` |
| `0x10c` | 215 | `munmap` |
| `0x120` | 222 | `mmap` |
| `0x12c` | 226 | `mprotect` |
| `0x138` | 64 | `write` |
| `0x144` | 63 | `read` |
| `0x150` | 56 | `openat` |
| `0x15c` | 57 | `close` |
| `0x168` | 94 | `exit_group` |

九条里**没有** `clone`（220）、`fork` 或 `execve`（221）系统调用封装。此前 `libdexvmp.so` 统计的 34 个 `svc` 位置中，**9 处属于该共用尾段**，其余 **25 处**位于另一段原生可执行代码，存在动态/混淆计算系统调用号的情况，此次尚未证明是否包含任何子进程创建动作。

因此，不能因 `libdexvmp` 的 34 个 `svc` 就认为该库独有这些内核能力，也不能把共同尾段的 `exit_group` 直接当成 DEC 警告后的退出调用证据。

## 三、确切的原生辅助程序行为

对共享尾段的 ARM64 指令反汇编后，能够进一步固定以下行为：

- 尾段相对偏移 `0x238`、`0x240`：`adrp/add` 构造存储于相对偏移 `0x9f4` 的 `/proc/self/maps` 路径。相对 `0x268` 的 `bl` 调用该段内 `openat` 封装。
- `0x294` 调用 `read` 封装，后续指令按换行边界处理文本、比较目标字符串；在特定分支下 `0x308` 还调用 `exit_group` 封装，`0x310` 调用 `close`。
- 相对 `0x5e4`：`mov w2,#7`，与 `0x614` 的 `bl mprotect` 对应，指令参数为 `PROT_READ|PROT_WRITE|PROT_EXEC`。这能证明代码内含将某段映射设为 RWX 的调用路径，但**不能据此证明运行时某一个匿名 RWX 映射必由它创建**。
- 相对 `0x1d8` 的 `dc cvau`、`0x1fc` 的 `ic ivau`、`0x20c` 的 `isb`，连同其调用位置，支持该段具有写入/调整可执行代码后维护 ARM64 指令缓存的功能。

上述结论使用确切字节指令和相对位置验证，区别于仅搜索字符串。它们为**共用装载/保护辅助代码**的解释提供强证据；是否真正运行以及作用于哪个内存区域，仍需运行时栈或内存页归属证明。

## 四、对 DEC / 独立进程研究意味着什么

中国移动两轮干净启动均观察到单独 `app_process / RuntimeInit` 进程，且初始化时点相差仅 28 ms；第二轮还用 PPID 确认主进程至少有两个直接子进程。[独立 RuntimeInit 证据](2026-10-22-app-process-runtime-init.md) 已记录这些事实。

此次新结果使先前将 `libdexvmp` 尾部九条 `svc` 当作“本应用专用的子进程检测/创建机制”的线索明显削弱。它们在十份业务功能不同的 SO 中完整复用，具有一个原版加固签名字串，其中**不含子进程创建的直接 syscall 封装**。

另一方面，`libDexHelper.so` 未包含本次 2,565 B 指纹，之前 ADB 实测早期始终映射 `libDexHelper.so`，而 `libdexvmp.so` 的映射还没有被采样到。后续更应追踪**实际运行的 native/ART 入口**，不能仅凭落在 APK 的静态代码推导真正的检测归属。

`DeviceEnvironmentCheck.startCheck()`、`DECRunning`、`DECMsgDialog` 的方法体及具体 Root 判定规则，仍然未恢复。
