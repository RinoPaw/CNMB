# 12.5.5：174 份 ARM64 SO 共用的原生保护尾段

核验日期：2026-10-22。证据唯一来源为中国移动 12.5.5 原版 APK，SHA-256 `6282d2cf05f76f37a60fff322bcf0d6f1d876829e5c9c4eae5cdd93b7a972a83`。全部偏移为原始 ELF **文件偏移**；虚拟地址单独标注。脚本与合成测试入库，商业 APK / SO 不上传。

## 关键更正：从 10 份扩大到 174 份

初版以 `libdexvmp.so` 的 `0x7f078` 处可执行尾段为参考，使用相对范围 `[0x20,0xa25)` 的 2,565 字节作为搜索指纹，仅匹配到 **10** 份 SO。这一范围多包含了 `0xa24` 的一个变化字节，导致**164 个假阴性**。

将指纹缩至相对范围 **`[0x20,0xa24)`，长度恰为 2,564 B**，重新扫描原版 APK 中**全部 191 个 `lib/arm64-v8a/*.so`**，结果如下：

| 核对指标 | 结果 |
| --- | ---: |
| APK 内 ARM64 `.so` 条目 | **191** |
| 有相同 2,564 B 可执行核心的 SO | **174** |
| 在此基础上多匹配第 2,565 字节的 SO | **10** |
| 未找到该共同尾段的 SO | **17** |
| 每段长度 / 可执行 ELF 段长度 | **2,640 B（`0xa50`）** |
| 各段完整 2,640 B 相对参考段的最大不同字节数 | **31** |
| 不同字节可能出现的位置 | **36 个字节位置**（9 个在头部，27 个在尾部） |
| 174 个样本中，相对偏移 `0xa24` 的不同取值 | **46 种** |

再进一步核对 ELF64/AArch64 类型（`e_machine=183`）、对应区域是否是可执行 `PT_LOAD`、全部九个系统调用封装、`/proc/self/maps` 常量、`mprotect` 和指令缓存操作，**174 个均通过**。这项结果是原始字节与结构的交叉验证，且已在本地原版诊断 ZIP 上重跑。

最初命中的十个库（额外第 2,565 个字节一致）：`libAlipayBitmapNative.so`、`libdatabase_sqlcrypto.so`、`libdatajar.so`、`libdexvmp.so`、`libentryexpro.so`、`libijkrecorder.so`、`libijksdl.so`、`libmmkv.so`、`libv8worker-native.so`、`libyewu.so`。它们是 **174 个命中中的子集**。

没有该共同尾段的 17 个库：

- `libDexHelper.so`、`libdexjni.so`
- `libZWRisk-v7_6_4r_61803305.so`、`libZWRiskComm-v7_6_4r_61803305.so`
- `libkh.so`、`liblbs.so`
- `libsgmain.so`、`libsgmainso.ucb.so`、`libsgmainso.version.so`
- `libsgmiddletier.so`、`libsgmiddletierso.ucb.so`、`libsgmiddletierso.version.so`
- `libsgmisc.so`、`libsgnocaptcha.so`
- `libsgsecuritybody.so`、`libsgsecuritybodyso.ucb.so`、`libsgsecuritybodyso.version.so`

注意，`libZWRiskComm` 的 APK 项实际是外层 ZIP 包装；这里的“未命中”只描述上述特定尾段，并未排除其他保护机制。

## 共同尾段的真实系统调用封装

所有 174 份均含相同的九处 AArch64 `mov x8,#number; svc #0; ret` 编码，经指令原始字节核验：

| 尾段相对 `svc` 位置 | 系统调用 | ARM64 Linux 编号 |
|---|---|---:|
| `0x100` | `write` | 64 |
| `0x10c` | `munmap` | 215 |
| `0x120` | `mmap` | 222 |
| `0x12c` | `mprotect` | 226 |
| `0x138` | `write` | 64 |
| `0x144` | `read` | 63 |
| `0x150` | `openat` | 56 |
| `0x15c` | `close` | 57 |
| `0x168` | `exit_group` | 94 |

该共同尾段**没有直接封装** `clone(220)`、`execve(221)`。`libdexvmp.so` 原来统计的 34 个 `svc` 编码，其中九个属于这种大范围复用的保护尾段，其余 25 个尚需独立控制流分析。不能将九处共享指令直接归给 DEC 的进程创建或退出行为。

## 其他原版指令与字符串证据

共同核心所有样本都包含：

- 字节序列 `__b_a_n_g_c_l_e__check1234567_`（尾段相对 `0x550`），是明确的原版保护标记；标记中出现 Bangcle 名称，但**不单凭字符串认定供应商、具体保护版本或其与 SecNeo/DEC 的关系**。
- `/proc/self/maps\0`（相对 `0x9f4`）；指令构造其地址，调用 `openat` / `read`，处理映射文本。
- `mov w2,#7` 和对 `mprotect` 封装的 `bl`，即尝试设置 `PROT_READ|PROT_WRITE|PROT_EXEC`。
- `dc cvau`、`ic ivau`、`isb` 等 ARM64 指令缓存维护操作。
- `exit_group` 的调用指令存在于辅助段的分支路径，但尚无运行时执行证据。

共同指纹来自代码区的 `2,564 B`，匹配后每份还必须通过 **2,640 B 整段、可执行 Program Header 和指令集**校验。全段不同字节只在开头、末尾出现，代码主体高度稳定；这些变量字段不应未经验证就解释成具体密钥或解密参数。

## 对 DEC 的意义与尚缺证据

此保护尾段出现在 **174/191** 的绝大多数 ARM64 库中，包括数据库、播放器、识别和其他业务 SDK。这一分布使其无法作为 DEC 专用代码的特异性标记。尤其 `libDexHelper.so`、`libdexjni.so` 没有这种尾段，且第一轮 ADB 快照确认 `libDexHelper.so` 很早就映射进进程；应继续追踪其真实 JNI/ART 装载链。

现在仍未确认：共同尾段是否在本轮启动阶段实际执行、是否创建了观察到的匿名 RWX 页、是否触发 `DECMsgDialog`、`DeviceEnvironmentCheck.startCheck()` 的实际实现存于何处，以及额外 `app_process` 的创建入口。对于这些问题，当前数据只能提供候选调查方向。
