# 12.5.5：原版 Dalvik 进程操作调用与 ARM64 系统调用表面调查

取证日期：2026-10-22。基于 SHA-256 固定的中国移动 12.5.5 原版 APK（`6282d2cf05f76f37a60fff322bcf0d6f1d876829e5c9c4eae5cdd93b7a972a83`），所述地址均为原始 ARM64 `.so` 的**文件偏移**。此次调查旨在缩小两轮实测重复出现的独立 `app_process / RuntimeInit` 进程的可能实现范围。

## 1. 14 个已恢复 Dex 片段的显式调用候选统计

使用 [`tools/audit_process_calls.py`](../tools/audit_process_calls.py) 遍历已验证的 14 组 `class_defs` 与所有可解析的 `code_item`，寻找 16-bit 对齐并具有 Dalvik `invoke-kind` 操作码（`0x6e–0x72`、`0x74–0x78`）的目标方法索引：

| 原版方法签名类别 | 命中候选总数 |
| --- | ---: |
| `java.lang.Runtime.exec` | **61** |
| `java.lang.ProcessBuilder.start` | **12** |
| `android.os.Process.killProcess` | **32** |
| `java.lang.Runtime.exit` | **2** |
| **总计** | **107** |

这是**原版方法引用和 Dalvik 编码字节共同支持的调用候选数**。扫描不属于完整 CFG/变长指令与 payload 识别器，因此不能断言每个命中都是可达、实际执行的调用；不同 Dex 的方法索引必须在各自索引空间解释。

具体的原版方法体示例：

- `Lcom/mc10086/lib/tools/root/RootBeer;`：在 `checkForDangerousProps`、`checkForRWPaths`、`checkSuExists` 中共找到四条 `ProcessBuilder.start` 调用候选，文件偏移 `0x4107022`、`0x410708c`、`0x4107180`、`0x4107324`。
- `Lcom/chinamobile/ots/util/common/DeviceInfoUtil;`：原版 `checkRoot` 为 Dex 方法 ID **9038**，`code_item @0x87fa890`；方法体中 `Runtime.exec` 候选位于 `0x87fa8b2`，实际 `const-string` 包括 `su`（`0x87fa8ac`）、`echo "Do I have root?" >/system/sd/temporary.txt\n`（`0x87fa8cc`）及 `exit\n`（`0x87fa8d8`）。**对该片段所有可解析代码项扫描，未找到直接调用其 `checkRoot` 方法 ID 9038 的候选。**
- `Lcom/mc10086/lib/tools/AppManager;` 的 `killAllProcess` 包含两条 `Process.killProcess` 候选，`Lcom/mc10086/lib/tools/CustomCrash;` 的 `uncaughtException` 也包含终止进程调用。
- 大量其他候选分布在支付宝、腾讯、地图、性能分析及设备信息工具组件中。**没有足够的调用路径证据将其与 DEC 关联。**

特别重要的是：**包含 `DECApp` 实际实现的第一组 Dex 片段（可见字符串索引表 `0x2500c`）没有对上述 `Runtime.exec` 或 `ProcessBuilder.start` 的目标方法引用。** 这也与已恢复的 `DECApp.onCreate / intiDECabcOnCreate` 方法体一致。该结论范围严格限制为恢复的片段；`DeviceEnvironmentCheck.startCheck()`、`DECRunning` 和 `DECMsgDialog` 的方法体仍未定位。

## 2. 四份加固载体 ELF 的 ARM64 `svc` 指令候选

使用 [`tools/audit_native_svc.py`](../tools/audit_native_svc.py) 解析原始 ELF64/AArch64 的 **`PT_LOAD` 且具可执行权限的原始文件字节**；按 4-byte 对齐和 ARM64 `svc` 指令编码掩码 `(word & 0xffe0001f) == 0xd4000001` 筛查：

| 原版 SO | `svc` 编码候选 |
| --- | ---: |
| `libDexHelper.so` | **0** |
| `libdexjni.so` | **0** |
| `libdexvmp.so` | **34** |
| `libdatajar.so` | **9** |

`libdexvmp.so` 的多数候选位于主可执行 `LOAD` 文件片段，另外九条位于 `0x7f178–0x7f1e0`；`libdatajar.so` 的九条在其末尾的辅助可执行片段 `0x9762178–0x97621e0`。这些地址是 `svc` **指令编码位置**，不代表已经动态执行。能看到 `svc` 编码也不能单独得到系统调用号；准确辨认需分析执行到该处时 `x8` 寄存器的值、条件跳转和代码是否可达。

`libDexHelper.so` 及 `libdexjni.so` 的已保存可执行 `PT_LOAD` 中没有 `svc` 字节，也无法据此排除它们通过 libc、动态装载或运行时转换后的代码进行系统调用。此前已观察到匿名可执行/RWX 映射；**没有证据证明其内容属于哪一份 SO 或触发子进程的具体指令**。

另外，直接检查 `libdexvmp.so` 的 ARM64 指令发现四处 `mov w8, #0xdc`，位置为 **`0x1a808`、`0x1ac44`、`0x1dae0`、`0x1e9d0`**。尽管 **220** 正好是 ARM64 Linux 的 `clone` 系统调用编号，这四处后续指令实际都是 `strb/sturb w8,[stack]`，随后 `ldr x8,[x19,#0x18]` 覆盖寄存器并通过 `blr x8` 跳转。它们用于构造栈上的数据字节，**不能证明调用了 clone**。已将逐指令机器码断言加入原生审计工具，以防止仅根据常数 `220` 误判进程创建。

这四份 SO 的原始明文 ASCII 字节中均未找到完整 `app_process` 子串。此为有限范围内的字面量检查，不能排除运行时生成命令、字符串混淆、路径分段或其他库。



### 2026-10-22 后续复核：十份库共用尾部装载辅助代码

之前统计的 `libdexvmp.so` 34 处 `svc`，其中 **9 处**实际属于独立的、2,640 字节 `r-x` `PT_LOAD` 辅助尾段；剩余 **25 处**位于该库自身前部的可执行区域。`libdatajar.so` 的全部 **9 处** `svc` 编码均在相同结构的尾段中。

原始 APK 的全部 **191 份 ARM64 SO** 经过精确的 **2,565 字节指令核心**扫描，确认至少 **10 份库**（包括 `libdexvmp`、`libdatajar`、`libmmkv`、`libijksdl`）具有相同辅助段。九条尾段 `svc` 的准确 syscall 编号为 `write(64)`×2、`read(63)`、`openat(56)`、`close(57)`、`mmap(222)`、`munmap(215)`、`mprotect(226)`、`exit_group(94)`。**尾段没有 `clone(220)` 或 `execve(221)` 的直接封装。**

辅助段还有 `/proc/self/maps` 读取、`mprotect(PROT_READ|PROT_WRITE|PROT_EXEC)`、ARM64 D/I-cache 刷新和保护标记 `__b_a_n_g_c_l_e__check1234567_`。详见 [十库共用原生尾段审计](12.5.5-shared-native-loader-tail.md) 与 [可复核脚本](../tools/audit_shared_native_tail.py)。其原版存在与运行时执行依旧属于不同证据层级，不能凭它归咎 DEC 的终止或反 Frida 行为。

## 3. 与两轮实际子进程实验的关系

两轮都在主进程启动约 4.75 秒后出现具有同一套系统库加载特征的独立 `RuntimeInit` 日志；第二轮确认主进程另有直接子进程，且一个短命进程首次被观察时 PPID 已为 1。详见 [独立 RuntimeInit 双轮取证](2026-10-22-app-process-runtime-init.md)。

**静态代码已确认**：应用包中同时包含 Java 运行命令、终止进程的代码，以及具 `svc` 指令的原生加固库。

**尚未确认**：上述哪条代码实际创建了第二轮的子进程；`libdexvmp.so` 是否在关键时刻映射/执行；`DeviceEnvironmentCheck.startCheck()` 是否使用进程派生、辅助进程 IPC 或 native 检查；哪项具体规则决定 DEC 弹窗。

不得将候选字符串、静态方法存在、实际方法调用和运行时因果关系混为一谈。

## 4. 原版样本复核

```powershell
python .\tools\audit_process_calls.py .\path\to\base.apk
python .\tools\audit_native_svc.py .\path\to\base.apk
```

两份工具均为只读；`inspect_dec_tables.load`、`inspect_native_loader.read_apk` 会校验固定的原版样本哈希。公开仓库不含原始商业 APK、SO、设备日志或进程命令行。
