# 中国移动 12.5.5：`libDexHelper` 与 `libdexjni` 的引导构造函数

日期：2026-10-22。仅使用原版 APK 及其原始 ELF 字节直接验证，不使用网络上的通用壳实现解释当前代码。复核工具：[tools/audit_protector_constructors.py](../tools/audit_protector_constructors.py)。用户设备私有日志和原版 SO 均不入库。

## 一、`libDexHelper.so` 的加载构造函数有明确 ELF 证据

原版 `libDexHelper.so` SHA-256：
`6b5abe051e75d630d5447785d1f1a9f480b2c636f2874a7494767cfcde2ac4db`。

在 `PT_DYNAMIC` 可验证下列配置：

| 原版 ELF 动态条目/重定位 | 值 | 证明范围 |
|---|---|---|
| `DT_INIT_ARRAY`（25） | ELF 虚拟地址 `0x14d08` | 加载构造函数表 |
| `DT_INIT_ARRAYSZ`（27） | 16 B | 两个 8 字节表槽 |
| `DT_FINI_ARRAY`（26） | `0x14d18` | 卸载回调表 |
| `DT_RELA`（7） | `0x26e8` | 动态重定位位置 |
| `R_AARCH64_RELATIVE` | `r_offset=0x14d08, addend=0x4780` | 第一个加载构造函数指向 `0x4780` |
| `R_AARCH64_RELATIVE` | `r_offset=0x14d18, addend=0x2b10` | 卸载回调指向 `0x2b10` |

这两个指针均落于原版可执行 `PT_LOAD`（`[0,0x4ca0)`）内，其文件偏移与上表的虚拟地址相同。第二个 `INIT_ARRAY` 槽在原版文件中为零；**不能把 FINI_ARRAY 中的 `0x2b10` 错认成第二个启动构造函数**。

反汇编 `0x4780` 周围的 ARM64 原版指令，可以验证：

- `0x4780`：`sub sp,sp,#0x30`，函数入口；
- `0x4808/0x4810`：构造小端 `0x464c457f`，即 ELF 文件魔数；
- `0x4804` 到 `0x4838`：获取页面地址、比较该魔数，并在不匹配时回退一页继续搜索；
- `0x4850` 与 `0x485c`：调用本 ELF 的两个 PLT 跳转入口。

由此能够给出比“SO 里包含 `JNI_OnLoad` 字符串”更精确的装载入口：**原版动态链接元数据把 `0x4780` 作为本 SO 的加载时初始化函数**，该函数的原版机器码包含寻找自身 ELF 基址的程序逻辑。

但本报告尚未解析这两个 PLT 调用的运行时目标；ELF 构造函数的存在也不直接证明它负责创建辅助进程或执行 `DeviceEnvironmentCheck.startCheck()`。

## 二、`libdexjni.so` 具有结构相同的构造函数

原版 `libdexjni.so` SHA-256：
`f567dde1e581483f7da6680d87183b522493b5109f19ea27bf388fd80aec9199`。

它的 `DT_INIT_ARRAY=0x12d08`，第一条 `R_AARCH64_RELATIVE` 将该槽重定位至 **`0x2780`**；`DT_FINI_ARRAY=0x12d18`，第二条相对重定位指向卸载函数 **`0xb10`**。这些目标也落在本 ELF 的可执行加载段。

两份库的构造函数偏移恰好相差 **`0x2000`**，进一步作字节比较得到：

| 对比指标 | 原版验证 |
|---|---|
| `libDexHelper.so` 相同尾段 | 文件 `[0x295a,0x4ca0)` |
| `libdexjni.so` 相同尾段 | 文件 `[0x95a,0x2ca0)` |
| 完全相同的连续字节 | **9,030 B** |
| 其中可按 4 字节对齐解释的尾部 | 9,028 B |
| 相同片段 SHA-256 | `08ceab5789747cd32ea687615f47198489db37d2564b2841b083a1397992ff46` |

两段都含有原版 `JNI_OnLoad` 和 `/proc/self/maps` 字符串，位置分别相差 `0x2000`：`0x49f8 / 0x29f8` 和 `0x4a08 / 0x2a08`。这些 9,030 字节同时包含 ARM64 机器码和嵌入的只读字符串，**不可都称作代码指令**。

这种逐字节一致性，结合 `INIT_ARRAY`、`FINI_ARRAY` 的对应指针，是两个库复用原生引导组件的直接证据；无法由此确定两者的运行时作用完全相同。

## 三、与实际设备启动的证据关联

此前两轮纯 ADB 进程采样中，`libDexHelper.so` 都很早进入目标进程映射；当时的有效快照没有看到 `libdexjni.so`。结合本次原始 ELF 证据，**`libDexHelper.so:0x4780` 是下一步优先研究的确切 native 装载入口**。

证据层级仍须区分：

- **原始 ELF 直接证明**：动态链接器元数据配置了 `0x4780` 加载构造函数，并确认该函数包含 ELF 基址查找逻辑。
- **ADB 快照直接证明**：某次采样时 `libDexHelper.so` 文件被映射。
- **尚未直接证明**：该函数在对应快照前实际执行到哪一条指令；它是否创建了同名子进程；哪个函数加载或解密 `DeviceEnvironmentCheck` 类。

`libdexvmp.so` 和 `libdatajar.so` 中广泛复用的 Bangcle 标记尾段已有 [174 库共同保护尾段报告](12.5.5-shared-native-loader-tail.md)。那段通用代码的静态存在不能代替本次 `libDexHelper` 的启动证据，也不能自动视为 DEC 检测逻辑。

## 四、复核

```powershell
python .\tools\audit_protector_constructors.py .\path\to\base.apk
```

可使用相同 SHA-256 的原始诊断 ZIP。工具仅依赖 Python 标准库，对两份 SO 单独做哈希确认，逐段验证 ELF 类型、`PT_DYNAMIC`、`INIT_ARRAY`/ `FINI_ARRAY`、`R_AARCH64_RELATIVE`、可执行目标地址、`0x4780` 的关键 ARM64 指令，以及两 SO 完全相同的 9,030 B 引导区。
