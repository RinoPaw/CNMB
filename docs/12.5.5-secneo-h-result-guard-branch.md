# 中国移动 12.5.5：SecNeo H 管道结果后的原生判断与异常分支

验证日期：2026-10-24。仅使用 SHA-256 固定的原始中国移动 12.5.5 APK 与其内层 \`libDexHelper.so\` ELF，不使用社区资料。原版 APK SHA-256 为 \`6282d2cf05f76f37a60fff322bcf0d6f1d876829e5c9c4eae5cdd93b7a972a83\`；恢复后内层 ELF SHA-256 为 \`b0d42eb0d86a7fdd3c4e5669c46376d0d4c041da5adb3f5d0e3ccbe9f369ef54\`。

本报告续接[SecNeo H 的 Java 写入与 JNI 读端](12.5.5-secneo-h-pipe-result-chain.md)。原生代码位于原始 ELF 的独立工作线程函数 \`[0x59700,0x5b45c)\`，函数边界通过原始 \`.eh_frame\` 确认。由于保护代码没有清晰函数符号，\`llvm-objdump\` 对大范围代码沿用 \`JNI_OnLoad+offset\` 标记；所有下列地址采用原始 ELF 虚拟地址，与外层 SO 的偏移无关。

## 1. 从 readUTF 返回到整数比较

| 内层 ELF VA | 原版 AArch64 指令 / 数据流 | 限定结论 |
| --- | --- | --- |
| \`0x5ad18\` | \`bl 0x13dc4\`；结果进入 \`x20\` | 前面构造的 \`DataInputStream.readUTF\` JNI 包装 |
| \`0x5ad30–0x5ad38\` | JNI 虚表 \`+0x720\`；\`tst w0,#0xff\`；\`b.eq 0x5ae1c\` | \`ExceptionCheck == 0\` 进入正常读取结果路径；有异常进入不同清理路径 |
| \`0x5ae1c\` | \`cbz x20,0x5af6c\` | 返回字符串为空时不进入数值处理 |
| \`0x5ae30–0x5ae34\` | JNI 虚表 \`+0x548\`；\`blr x8\` | \`GetStringUTFChars\` |
| **\`0x5ae38\`** | **\`bl 0xebf0\`** | **\`atoi@plt\`** |
| **\`0x5ae3c\`** | **\`cmp w0,#1\`** | 整数比较阈值为 1 |
| **\`0x5ae40\`** | **\`b.lt 0x5af6c\`** | \`atoi\` 结果小于 1，进入清理及后续逻辑 |

这验证了已有报告中的阈值 \`>=1\`，而且精确确定该分支位置及它的互补路径。即使原版 \`H\` 默认 flags 为 0、写回 \`TracerPid\`，仍需区分 \`atoi\` 实际返回值与检测代码可能被改写/短路的其他运行时条件。

## 2. 整数大于或等于 1 后的状态字节分发

仅在 \`atoi()>=1\` 的路径上，原版的下一段指令为：

~~~text
0x5ae44: adrp x8,0x123000
0x5ae48: ldr  x8,[x8,#0xdc0]  ; 重定位槽（R_AARCH64_RELATIVE → 0x128000）
0x5ae4c: ldr  x8,[x8]         ; 再从运行时指针槽取指针
0x5ae50: ldrb w8,[x8,#0x17c] ; 取最终运行时对象第 0x17c 字节
0x5ae54: tbnz w8,#0,0x5af18
~~~

因此这个分支只测试**一个运行时字节的 bit 0**：

- bit 0 = 1：跳到 \`0x5af18\`，在那里构造后续内部对象、调用本 ELF 的内部函数 \`0x2616c\` 和 \`0x2682c\` 等。其具体业务语义尚未证实。
- bit 0 = 0：按指令流顺序进入 \`0x5ae58–0x5ae84\`，其中关键指令包括 \`mov w10,#0x1f8\`、\`mov x0,#0\`、\`mov sp,x0\`、\`mov x30,x0\`、\`br x10\`。写入 32 位 \`w10\` 会使 \`x10=0x1f8\`。这是一条**故意破坏执行上下文并跳向非常低地址的异常分支**。

只凭原版 ELF 就能证明这些指令及静态控制流。**仍无法断定**本机某轮是否真正执行了该分支，跳转后具体信号与崩溃地址是什么。早先 Tombstone 的 \`SIGSEGV 0x978/0x97c\` 与这里的显式常数 \`0x1f8\` 不同，不能据此直接归因。

## 3. 同一线程后段存在第二处受状态字节保护的异常分支

原版 \`0x5b334–0x5b344\` **再次读取同样形态的运行时指针链和对象的 \`+0x17c\` 字节**，执行 \`tbnz w8,#0,0x5b3c0\`。当 bit 0 为 0 时，其后续指令会清零 \`sp\`、\`x30\`，随后 \`br x11\`，此时 \`x11=0x1f0\`。

这一段说明相同的间接状态字段在**另一控制位置**参与异常分支选择。它处于稍后的逻辑段，是否能与上面的 TracerPid 阳性路径视为同一次运行的连续执行，还需要完整 CFG 和当次状态数据支持。

另在 \`0x5b3ac–0x5b3bc\` 存在 \`getpid\`、内部调用和 \`_exit(3)\`，该路径也不得仅凭空间相邻就归给前面的数值判断。

## 4. 找到一处可能相关的静态写入，但别名关系未闭合

独立位置 \`0x3af24\` 从栈 \`[sp,#0x7f0]\` 读取字节，\`0x3af28\` 检查非零，\`0x3af44–0x3af48\` 执行：

~~~text
adrp x12,0x12b000
strb w9,[x12,#0x17c]   ; 直接写入 0x12b17c
~~~

后面还有继续复制文本的字节循环。因此 \`0x12b17c\` 是另一个确实存在的原版存储点。当前 **不能认定** \`0x5ae50\` 所读取的运行时对象就是 \`0x12b000\`：读取端经 \`0x123dc0 → 0x128000 → [运行时指针]\` 间接寻址，两个地址的别名/赋值链以及执行时内容尚未独立恢复。特别不能简单将 \`+0x17c\` 视为具有已知语义的 Root/DEC 开关。

## 5. 当前证据边界与复核

目前可严格证明：

1. 原版默认 \`H\` 的 \`TracerPid\` 数值通过 \`writeUTF/readUTF\` 管道路径进入 native \`atoi\`。
2. \`atoi < 1\` 进入清理/后续分支；\`atoi >= 1\` 读取运行时 \`+0x17c\` 状态并分流。
3. 状态字节 bit0 为 0 的分支包含破坏 \`SP/LR\` 并跳向 \`0x1f8\` 的指令；另一处类似指令跳向 \`0x1f0\`。
4. 尚未建立这个检查结果与 \`DeviceEnvironmentCheck.startCheck()\`、\`DECMsgDialog\`、应用退出或特定设备崩溃之间的直接因果连接。
