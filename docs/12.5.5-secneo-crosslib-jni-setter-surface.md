# 中国移动 12.5.5：跨库 JNI 静态字段写入面

核验日期：2026-10-25。仅使用固定 SHA-256 原始中国移动 12.5.5 APK（6282d2cf05f76f37a60fff322bcf0d6f1d876829e5c9c4eae5cdd93b7a972a83），以及恢复后同样验证 SHA-256 的内层 ELF。研究工具没有修改 APK、手机或公开任何私有二进制。

## 扫描范围与方法修正

此前针对内层 libDexHelper.so 的完整 .text 已发现且验证两个 JNI SetStaticObjectField 写入点（0x2C5D8、0x2CAB8），均写 H.PC_FLAG。结论适用于该库，不适用于整个 APK。许多其它原生库剥离了节区表，因此按 .text 节区名称枚举会漏掉它们。本轮改为使用可执行 PT_LOAD 程序段，直接检查 ARM64 机器字。

| 指标 | 原始 APK 结果 |
| --- | ---: |
| lib/arm64-v8a/*.so | 191 |
| 可解析 ELF | **176** |
| 空文件、其它封装或非 ELF | 15 |
| 可执行 PT_LOAD 文件内容 | 92,840,901 字节 |
| LDR Xt,[Xn,#0x4D0] 原始候选 | 219 |
| 近期经指针加载、之后 BLR 调用的 JNI 形态候选 | 9 |

219 与 9 都是基于机器指令形式的**候选数**，不能当成调用次数或者 PC_FLAG 写入次数。普通对象字段也可能具有 +0x4D0 偏移。例如内层 libDexHelper.so 的 0xEC94 在 printf@plt 中加载 GOT 地址偏移 #0x4D0，显然不属于 JNI 写入。15 个非 ELF 文件中的内部封装内容、其他 CPU 架构，以及间接动态生成的执行代码不在此次扫描范围内。

## 直接验证的六处 SecNeo JNI SetStaticObjectField 调用点

根据各库的原版机器指令逐条确认三个步骤：从 JNIEnv 读取函数表（LDR x8,[x19]），从表偏移 +0x4D0 读取 SetStaticObjectField，随后 BLR x8。这是 JNI 函数表的直接调用。

| 原始文件 | LDR 函数表偏移位置 | BLR 位置 | 目标字段 |
| --- | --- | --- | --- |
| 内层 libDexHelper.so | 0x2C5D8 | 0x2C5E0 | **H.PC_FLAG**（先前已确定） |
| 内层 libDexHelper.so | 0x2CAB8 | 0x2CAC0 | **H.PC_FLAG**（先前已确定） |
| 内层 libdexjni.so | **0x8638C** | 0x863A0 | 运行时指定 |
| 内层 libdexjni.so | **0x863BC** | 0x863C8 | 运行时指定 |
| libdexvmp.so | **0x6A154** | 0x6A160 | 运行时指定 |
| libdexvmp.so | **0x6A244** | 0x6A258 | 运行时指定 |

验证的库哈希：
- 内层 libDexHelper.so：b0d42eb0d86a7fdd3c4e5669c46376d0d4c041da5adb3f5d0e3ccbe9f369ef54
- 内层 libdexjni.so：cb2a9ebd1a40fd7d0e42557c029ea1fa0405c487dd11b5bf1b10a5aea372b950
- 原始 libdexvmp.so：1003c91df71d44bb8d4e44dd0b89e4d708bf4422d27646863155b58e2ef65cfb

后两份库中的函数是**通用 JNI 字段操作分发器**，其原版源码级数据流具有更多实质证据：

| 库 | FindClass JNI 表加载 | GetStaticFieldID JNI 表加载 | 原版动态跳转表 |
| --- | --- | --- | --- |
| libdexjni.so | 0x862D4 | 0x862E8 | 0x8631C–0x86324 |
| libdexvmp.so | 0x6A1E8 | 0x6A1FC | 0x6A104–0x6A10C |

分发器会使用运行时提供的类名、字段信息、字段值执行 Java 静态字段访问。由此可以确认：**SecNeo 相关的其它原生库确有通用字段写入能力**。但它们本次的字段目标来自运行时输入，尚无原版直接证据证明其曾指向 H.PC_FLAG，更没有证据证明其写入了清除 bit0/bit1 的数值。

## 通用分发器调用者与字段值来源

本轮继续对两个通用分发器入口进行了原版 AArch64 全可执行 PT_LOAD 的**直接 BL 交叉引用扫描**：

- 内层 libdexjni.so 的分发器入口是 **0x86270**；只找到一处直接 BL，位于 **0x6680C**。该位置前的原版指令显示：`0x66800` 将保存的 JNI 环境指针移入 x0，`0x66808` 从 VM 栈槽 `[sp+0x908]` 加载 x1，而 `0x667F8` 通过 `[x9,x8,lsl#3]` 索引读取 x2。该函数随后进入 0x86270 的类/字段 JNI 分发流程。**字段描述与待写入值均为运行时 VM 输入，不能推断为 PC_FLAG。**
- libdexvmp.so 的分发器入口是 **0x6A0A0**。针对原版可执行 PT_LOAD 中的直接 BL，本次**没有找到调用这个准确地址的指令**。这项阴性证据严格局限于直接 BL，不排除 BLR、跳转表、间接函数指针或其它转发入口。

新增的只读审计现在强制验证上述两处函数入口的直接 BL 引用数量、0x667F8/0x66800/0x66808/0x6680C 的原始机器字，同时仍保留前面的六处 JNI 调用验证。证据方向已经从“哪些库有能力写 Java 静态字段”缩小到“哪些代码为这些分发器提供真实字段目标和新值”。

## 对此前结论的修正及研究边界

此前证明的两条 H.PC_FLAG 专用 Native 写入路径继续成立：sw(Context,int) 使用（原参数 OR 1），bs(Context,int) 使用（原参数 OR 2）；两者只会设置标志位。原始 Java 初始化值为 255，它会让 sw/bs 的标志位守卫提前返回。

本轮发现另四个通用写入点，说明原版确有间接修改 Java 静态字段的原生设施。接下来应检查两个通用分发器的**输入与真实类名、字段名**，尤其是它们是否可能收到 H.PC_FLAG 及不同于原值的低位。仅凭通用写入能力不能认定 PC_FLAG 曾发生清位，不能据此断言 IsoService 绑定或 DEC 弹窗有直接因果关系。

## 复核入口

新增 [跨库 PT_LOAD 审计工具](../tools/audit_secneo_crosslib_jni_setters.py) 与 [合成回归测试](../tests/test_audit_secneo_crosslib_jni_setters.py)。工具验证完整原版 APK 哈希、原版库哈希、可执行段、候选计数、六处实际 JNI 指令及两个动态分发器的 GetStaticFieldID 操作，不输出商业二进制文件。

运行示例：

~~~powershell
python .\tools\audit_secneo_crosslib_jni_setters.py .\path\to\original-base.apk
~~~

也接受包含 apks/01-base.apk 的原始诊断 ZIP。扫描阴性证据严格局限于上述可解析的 ARM64 可执行 PT_LOAD 和明确的 JNI 指令形式，未排除经过其它寻址计算、JNI 函数指针传递、Java 反射及动态加载代码的写入。
