# 中国移动 12.5.5：Java 可读取 envc.push 的两个 JNI 接口

核验日期：2026-10-24。原版 APK SHA-256：`6282d2cf05f76f37a60fff322bcf0d6f1d876829e5c9c4eae5cdd93b7a972a83`；原版 `classes.dex` SHA-256：`6abbe8c56cc92a5d33cc12b2fdfda9a487325382e62b321359db65c98a27ca17`；内层 `libDexHelper.so` SHA-256：`b0d42eb0d86a7fdd3c4e5669c46376d0d4c041da5adb3f5d0e3ccbe9f369ef54`。研究仅使用先前保存的原始诊断 ZIP，未修改手机或 APK；文件内容及私有二进制均未公开。

此前[原生 root 记录审计](12.5.5-secneo-h-envc-push-root-record.md)找到了 `0x2682c` 在 `envc.push` 读取键名、状态字节与十六进制标识，以及不同检测路径对这些数值的条件写入。这次发现**原版 JNI 注册表直接暴露了其中两个读取结果**。

## 1. 原版 H 中存在真正的 Native 声明

从原始 `classes.dex` 的 `method_ids`、`class_defs` 与 `class_data` 读取，确认 `Lcom/secneo/apkwrapper/H;` 定义：

| DEX method index | 声明 | access flags | code_off |
| ---: | --- | --- | --- |
| 138 | `native gha(Ljava/lang/String;)I` | `0x109` | `0` |
| 139 | `native ghc(Ljava/lang/String;)J` | `0x109` | `0` |

`0x109` 包含 `public`、`static`、`native` 三位属性。这两项在小型原始 `classes.dex` 中没有 Java 方法体。

对**这份 `classes.dex` 的代码项**扫描已知 Dalvik `invoke-*` 编码，目前没有找到直接调用这两个方法的候选。这属于严格局限在该单一 DEX 的结果；可能存在运行时加载的其他 DEX、反射调用、其他 Java 入口及本轮未检查的动态调用。**不能据此推断没有真实调用者。**

## 2. JNI_OnLoad 的注册表直接关联到两个原生函数

原版 `JNI_OnLoad` 中的以下指令可独立复核：

| ARM64 地址 | 原版数据流 |
| --- | --- |
| `0x17490–0x17498` | 以运行时选中的 Java 类名字执行 JNIEnv `FindClass` |
| `0x174A8–0x174B0` | `NewGlobalRef`，把类引用写入运行时实例的 `+0x160` |
| `0x16010` | 从该运行时实例的 `+0x160` 获取注册目标类引用 |
| `0x16118` | 本次 `RegisterNatives` 的表项数量为 **6** |
| `0x160F8/0x16104` | `adrp/add` 建立函数地址 **`0x367A4`** |
| `0x161C0` | 将第一个方法的签名地址及函数指针保存到注册表 |
| `0x161C4/0x161D4` | 建立函数地址 **`0x36814`** |
| `0x1629C` | 将第二个方法签名地址及函数指针保存到注册表 |
| `0x164F8–0x164FC` | JNI 虚表 `+0x6B8` 调用 `RegisterNatives` |

原版 ASCII 字符表由 `JNI_OnLoad` 解码；此处寄存器 `x28` 指向可打印字符表 `+8`。依次读取真实 `LDRB W8,[X28,#imm]` 立即数，得到注册名和签名：

- **`gha`**，签名 **`(Ljava/lang/String;)I`**，函数地址 **`0x367A4`**。
- **`ghc`**，签名 **`(Ljava/lang/String;)J`**，函数地址 **`0x36814`**。

两项均与前述原始 `classes.dex` 的声明精确匹配。目标类来自运行时可覆盖的 SecNeo 类名配置，原始默认值已确认是 `com.secneo.apkwrapper.H`；旧 Logcat 的某一轮也确实观察到 `H` 的 Java 主入口。这一静态注册过程本身并不证明每轮设备都调用了两个 Native 方法。

## 3. 两个 JNI 方法分别返回记录状态和标识

对原始代码恢复：

**`gha(String)` → `0x367A4`**

- `0x367C8`：JNI `GetStringUTFChars` 将传入的 Java String 转为 C 字符串。
- `0x367DC`：`bl 0x2682C`，查询 `envc.push` 中指定键名的逻辑记录。
- `0x367E4`：把返回状态保存到 `w22`。
- `0x367F0–0x367F8`：JNI `ReleaseStringUTFChars`。
- `0x367FC`：`and w0,w22,#0xff`，返回状态的低八位，类型 `int`。

**`ghc(String)` → `0x36814`**

- `0x36834`：JNI `GetStringUTFChars`。
- `0x36840`：`x1=sp+0xc` 作为 `0x2682C` 的可选输出地址。
- `0x36848`：输出槽先清零。
- `0x3684C`：`bl 0x2682C`。
- `0x36860–0x36864`：JNI `ReleaseStringUTFChars`。
- `0x36868`：从 `[sp,#0xc]` 读取 `w0` 返回。该方法声明为 Java `long`，实际从 **32 位输出槽零扩展**到寄存器。结合 `0x2682C` 内部的 `strtoul(...,16)` 和输出参数写入，确认返回的是记录的十六进制标识对应数值。

这使原版静态数据流进一步贯通：

```text
                      envc.push
                          │
                       0x2682c
                      /       \
               0x367a4       0x36814
                gha(String)I  ghc(String)J
                 状态低8位    十六进制标识（32位来源）
                      \       /
                 com.secneo.apkwrapper.H
                   Java Native 接口
```

## 4. 剩余研究边界

已直接验证 **Java 可以通过注册于 H 的 Native 接口查询原生 `envc.push` 状态**。上层 Java 是否在目标应用的运行时动态 DEX 中调用 `gha` 或 `ghc`，还需要单独定位真实调用者。特别是没有找到 `DeviceEnvironmentCheck.startCheck()`、`DECMsgDialog` 或此前原生崩溃和这些方法之间的直接调用关系。
