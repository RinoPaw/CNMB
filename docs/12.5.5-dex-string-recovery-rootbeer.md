# 12.5.5：恢复受保护字符串索引与 RootBeer 方法体

日期：2026-10-22。样本仍为 SHA-256 `6282d2cf05f76f37a60fff322bcf0d6f1d876829e5c9c4eae5cdd93b7a972a83` 的原版 APK。所有偏移都是 `lib/arm64-v8a/libdatajar.so` 的**文件偏移**。

本报告由原始 SO 字节提取及 [工具](../tools/inspect_rootbeer.py) 的固定样本断言支持；不从网上 RootBeer 的其他版本外推当前客户端行为。

## 一、被遮蔽的 `string_ids` 仍可恢复

此前识别的两个 Dex 片段，各有约 128 KiB 的早期索引区域无法直接读取，然而相关 `string_data_item` 依旧明文、连续存储。每个字符串包含 ULEB128 长度前缀和终止 NUL。已知第一个可见索引的位置后，可以从其 `string_data` 地址向前追踪每一个 NUL 分隔边界，**恢复 32,740 个隐藏索引的字符串地址**。

交叉验证：

| 片段 | 第一个可见字符串数据 | 回溯得到 string_id 0 的地址 | 验证 |
| --- | --- | --- | --- |
| 第一组（DECApp） | `0x3db003` | `0x1e9b51` | 紧跟 16,526 个有效 `class_defs` 的结束位置 |
| 第三组（RootBeer） | `0x3babf6a` | `0x39a79bd` | 紧跟 7,201 个有效 `class_defs` 的结束位置 |

第三组 `RootBeer` 字符串 ID **21946** 回溯到 `0x3b0921e`，随后文本确为 `Lcom/mc10086/lib/tools/root/RootBeer;`。该验证独立于 `string_ids` 被遮蔽区域本身。

第一组早期字符串由此恢复出 `string_id 6175 = "/proc/"`、`6173 = "/cmdline"`，与之前已还原的 `Process.myPid()`、`FileReader`、`BufferedReader.readLine()`、`getPackageName()`、`String.equals()` 的指令对应。因此，现在可确认 `DECApp.isMainProcessDECabc()` 读取 `/proc/<当前 PID>/cmdline` 比较包名，再决定是否继续调用 `DeviceEnvironmentCheck.startCheck()`。

**注意**：回溯恢复的是已有字符串数据的索引位置，不意味着早期字节码或加固代码整体完成解密。恢复前会核对 NUL 边界和固定样本 SHA-256；推广到其他版本需要重新验证。

## 三、原版 RootBeer 确实包含的检测

| 方法 | 编码 ID | 实际字节码内容 |
| --- | ---: | --- |
| `checkForDangerousProps` | 47941 | 使用 `getprop`，检查 `ro.debuggable` 的 `1` 与 `ro.secure` 的 `0` |
| `checkForRWPaths` | 47943 | 使用 `mount`，比较 `rw` 挂载选项 |
| `checkForSuBinary` | 47945 | 使用字符串 `su`，调用 `checkForBinary` |
| `checkSuExists` | 47946 | 使用 `which` 与 `su` |
| `detectTestKeys` | 47953 | 检查 `test-keys` |
| `checkForRootNative` | 47944 | 调用 `canLoadNativeLibrary`，再走本地 Root 检查入口 |
| `isRooted` | 47955 | 串联应用包检测、`su`、属性、挂载、测试密钥和 native 检查 |

`isRooted()` 已验证的调用顺序：

```text
detectRootManagementApps()
detectPotentiallyDangerousApps()
checkForBinary("su")
checkForDangerousProps()
checkForRWPaths()
detectTestKeys()
checkSuExists()
checkForRootNative()
```

**重要更正**：`canLoadNativeLibrary()`（47938，`code_item @0x4106f74`）的完整指令是 `12 10 0f 00`，即 `const/4 v0, #1; return v0`，在此编译版本中**恒定返回 true**。不能将其解释成恒定返回 false，也不能因此推断真正的 native 检查必然成功。

## 四、不能认定这些方法触发了 DEC 弹窗

对第三组 Dex 的全部 **50,652** 个带代码方法进行 16 位对齐 `invoke-*` 候选扫描，匹配到 **27** 个 RootBeer 方法调用候选，全部位于 `RootBeer` 内部。

- `RootBeer.isRooted()`：直接调用点候选 **0**
- `RootBeer.isRootedWithoutBusyBoxCheck()`：直接调用点候选 **0**
- `RootBeer` 方法被其他类直接调用的候选：**0**

扫描包含已恢复的这段 Dex 中全部代码项，但还未实现支持每种 Dalvik 指令/payload 的完整控制流反汇编；动态反射、其他 Dex 片段及运行时加载的代码也不在该统计范围内。

因此，此次确认的是**原版 APK 包含 RootBeer 检测模块及其具体实现**，尚无证据表明 `DECApp`、`DeviceEnvironmentCheck` 或警告窗口实际调用了它。

## 五、复核

```powershell
python .\tools\inspect_rootbeer.py .\path\to\base.apk
```

需提供经过 SHA-256 验证的原始 APK、诊断 ZIP，或从同一原版提取的 `libdatajar.so`。公开仓库不保存 APK、SO 和未经脱敏的日志。

后续优先继续查找 `DeviceEnvironmentCheck` 的实际类定义及方法体，并判断它是否通过其他 Dex 或 native 组件实现检测。
