# 中国移动 12.5.5：SecNeo H 辅助进程与管道 IPC 的证据边界

核验日期：2026-10-24。仅依据原始 APK 的已验证 ARM64 指令、同一轮 `CNMB-after-reboot.txt` 的设备 Logcat 和公开仓库中已复核的原版代码报告。本文件不包含商业客户端二进制、完整 Logcat、FD 指向路径或私有内容。

## 原版代码已证明的管道传参

受保护内层 `libDexHelper.so` 中，线程入口 `0x59700`（由原版 `.eh_frame` 确定边界）包含：

- `0x5A3D0`：调用 `pipe@plt`。
- `0x5A418` 和 `0x5A4C4`：两次 `fork@plt`，属于同一个工作线程的控制流。
- `0x5A404`：将**运行时管道写端 FD** 格式化为十进制字符串；`0x5A40C` 复制该字符串。
- `0x5A710`：调用 `execl("/system/bin/app_process", "/system/bin/app_process", "/system/bin", "--nice-name=zygote", <入口类>, "--write-fd", <FD字符串>, "--flags", "0", NULL)`。原版默认入口类由独立指令数据流恢复为 `com/secneo/apkwrapper/H`，且运行时可覆盖。

详见[线程和原版参数数据流](12.5.5-inner-app-process-argv-thread-chain.md)。这一序列直接确认**原生进程启动路径向 Java 主类传递一个可写端 FD**。目前尚未恢复 `H` 的对应参数读取、写入内容、父端的读取及消费函数，不能据此断言管道携带 Root/DEC 检测结果。

对整个 1719 行日志进行逐 PID 检索，**该日志没有提供 PID 8714 的管道 FD、父进程的读端、`read`/`write` 系统调用或实际交换的数据**。同样，`Shutting down VM` 不能用作进程实际死亡的精确时间。故静态 `--write-fd` 和运行时 `H` 入口相互印证一个进程启动机制，但 IPC 通路还缺少动态对应。

## 新实验：只读取证共享管道 FD

新增 [`experiments/capture_shared_pipes.py`](../experiments/capture_shared_pipes.py)。更新后的采样器查询 `ps -A -o PID,PPID,UID,NAME`，先以确切包名确认应用的数字 UID，再纳入采样时同 UID 的其他进程（即使进程名暂时为 `app_process`、`zygote` 或已经被覆盖）。在 Root 权限下只检查候选进程的 `/proc/PID/fd` 中匿名管道的软链接及 `/proc/PID/fdinfo/FD` 的访问标志，不读取 FD 的数据，也不注入 App。同 UID 属于扩大候选范围的身份线索，不能证明所有候选进程都由 SecNeo 创建。

程序仅报告**同一时刻两个及以上同 UID 候选 PID** 持有相同匿名管道 inode 的情况，记录每一方的 PID、FD 编号、瞬时 PPID 和读/写访问模式。管道 inode 在导出 JSON 时替换为单次采集内部稳定的 `pipe_1`、`pipe_2`；完整的软链接目标、应用命令行、系统套接字、文件内容均不会输出。

先确认 ADB 已连接、Frida 服务端没有运行；此命令会重启应用，**不会清除应用数据**：

```powershell
python .\experiments\capture_shared_pipes.py --launch --seconds 18 --poll-seconds 0.2 --output .\captures\shared-pipes-local.json
```

如果 App 已运行，去掉 `--launch` 即可纯观察。设备必须已经授予 `su` Root 权限；程序在重启前检查 Root 可用，权限不足则停止。命令的实际轮询频率受 ADB/Root 调用耗时限制，设定 `0.2` 秒并不保证每 200 毫秒完成完整采样。

**结果解读：**

- 出现相同 `pipe_N` 且一个 PID 的 `access_mode=write`、另一个 `access_mode=read`：直接证明采样瞬间存在可通信的管道两端。若同时观察到与 `H` 对应的 PID，再结合其当次 AndroidRuntime 日志可将 IPC 候选范围收窄到具体进程。
- 同一 inode 在两个 PID 下均为 `write` 或均为 `read`：证明描述符指向同一管道，但无法据此恢复数据流向。
- 没有共享管道：只能说明采样未观察到目标进程间的共享 FD。双重 fork、FD 关闭及 PID 快速重托管可能使真正的通信时段非常短；另一端还可能属于包名不同的临时进程。
- 读写端匹配本身**无法证明**进程亲缘关系、数据已经传送、消息语义或 DEC 因果。还需要原版 `H` 字节码和父端 native `read` 的调用链。

输入/输出都属于私人运行时材料，`captures/shared-pipes-local.json` 位于仓库已经忽略的 `captures/` 目录，应当仅保存在本地，公开仓库只保留已脱敏的结论；该工具仅通过合成测试，**尚未在目标设备实测**。

## 首轮实测结果与修复

用户在 OPPO CPH2127、ADB Root 可用的环境中运行 18 秒，工具执行 34 次轮询，没有报出同名进程间共享管道，也没有采集异常。旧版只在共享集合变化时输出事件，缺少每轮选中 PID 和实际扫描的 FD 数量，因此这次阴性结果存在明显观测盲区。

2026-10-24 改进：采样时纳入已确认应用 UID 的所有进程名，增加 `statistics` 字段，包括 `polls_with_confirmed_uid`、`polls_with_same_uid_other_name`、`polls_with_two_or_more_candidates`、`fd_queries`、`total_pipe_fd_rows` 等；同时修复 Python 字符串转义的 `SyntaxWarning` 和 shell `printf` 的换行问题。更新后的逻辑只经过合成测试与 CI，尚未取得第二轮设备实测。即使 `total_pipe_fd_rows > 0`，也可能找不到跨 PID 共享，不能据此否定其他 IPC 路径。


## 第二轮真实设备取证与扫描有效性检查（2026-10-24）

同一 OPPO CPH2127 在 Root 可用的情况下执行：

```powershell
python .\experiments\capture_shared_pipes.py --launch --seconds 18 --poll-seconds 0.1 --output .\captures\shared-pipes-v2.json
```

用户给出的脱敏 JSON 显示：`polls=37`；`polls_with_confirmed_uid=37`；`polls_with_same_uid_other_name=11`；`polls_with_two_or_more_candidates=21`；`fd_queries=21`；`max_candidate_pids=4`；`total_pipe_fd_rows=0`；`errors=[]`。

这说明当前版本能发现同 UID 的非包名进程，并至少 21 次尝试采集两个及以上候选进程的管道 FD。但返回零行仍存在**采集有效性盲区**：原工具没有记录 `/proc/PID/fd/*` 实际枚举的软链接数量、`readlink` 成功次数，也无法辨认查询命令未输出与成功扫描后未匹配的情况。故第二轮结果未能证明进程没有管道。

新增的第三版工具在每个 PID 扫描结束时输出纯计数 `STAT`，本地解析为以下统计，不公开 proc 路径和匿名管道 inode：

- `verified_fd_probe_polls` / `incomplete_fd_probe_polls`：实际有无收到全部 PID 的计数证明。
- `total_fd_symlinks_seen`：实际枚举的符号链接数。
- `total_fd_readlinks_succeeded`：能解析软链接目标的次数。
- `total_pipe_symlinks_seen`：目标确实是 `pipe:[inode]` 的次数。
- `total_pipe_fd_rows`：成功输出、通过格式校验的管道 FD 行数。

请将第三版结果按顺序判断：

1. `incomplete_fd_probe_polls > 0`：shell 扫描或权限/设备行为使部分 PID 缺少有效计数，需先修复采集。
2. `total_fd_symlinks_seen > 0` 但 `total_fd_readlinks_succeeded=0`：FD 软链接目标读取受阻，当前阴性结论无效。
3. `total_pipe_symlinks_seen > 0` 但 `total_pipe_fd_rows=0`：管道类型已出现，但输出/解析路径异常。
4. 上述各项有效且 `total_pipe_fd_rows>0`、`shared_links=[]`：目标样本里存在管道，当前采样未发现两个候选 PID 的同 inode；仍不能排除瞬态通信或其他 UID 的父进程端点。

第三版也增加了 Linux 本地 `os.pipe()` 的实际 shell 扫描回归测试，证明在 GitHub Actions 的 Linux 执行环境能正确枚举、解析管道；目标手机上的有效性仍需用这些计数确认。

```powershell
git pull
python .\experiments\capture_shared_pipes.py --launch --seconds 18 --poll-seconds 0.1 --output .\captures\shared-pipes-v3.json
```

## 第三轮设备数据：确认没有真正读到任何 FD（2026-10-24）

用户在同一台 OPPO CPH2127 上运行 v3，得到：

- 37 次轮询，21 次同 UID 多 PID 的 FD 扫描，最多 4 个候选 PID。
- 11 次存在同 UID 的其他进程名。
- `verified_fd_probe_polls=21`、`incomplete_fd_probe_polls=0`，同时 `total_fd_symlinks_seen=0`、`total_fd_readlinks_succeeded=0`、`total_pipe_symlinks_seen=0`。
- `errors=[]`、`shared_links=[]`。

**纠正 v3 的统计解释：** `verified_fd_probe_polls` 当时只要求收到 shell 返回的 `STAT` 行，这只能确认脚本结束，**没有证明能访问或列举出 FD**。尤其当 `[ -L "$path" ]` 被系统拒绝或 `/proc/PID/fd/*` 无法展开时，之前会静默返回全零。此结果没有证据证明目标 IPC 不存在。

v4 在 shell 中分别统计 `fd` 目录是否存在、是否可读、是否可搜索，glob 展开获得的候选数、`test -L` 识别数与独立 `readlink` 成功数。去掉 `test -L` 作为调用 `readlink` 的门槛。新增 `fd_probe_no_access` 错误，任何一轮无有效 `readlink` 的采样都不会被计作成功访问 FD。

```powershell
git pull
python .\experiments\capture_shared_pipes.py --launch --seconds 18 --poll-seconds 0.1 --output .\captures\shared-pipes-v4.json
```

**根据计数区分故障来源：** `total_fd_dir_exists=0` 表示候选进程 FD 目录不存在/不可辨认；`total_fd_dir_readable=0` 或 `total_fd_dir_searchable=0` 提示权限或 Android procfs/SELinux 约束；目录存在且可读、`total_fd_glob_matches=0` 则表示目录枚举为空或无法展开通配符；glob 有候选、`total_fd_readlinks_succeeded=0` 表示解析符号链接失败。任何一项出现前，都不能据 `shared_links=[]` 排除管道。

## 第四轮：FD 目录存在，但当前 su 上下文没有读取能力

实测 v4：`polls=39`，同 UID 其他进程出现 12 次，含至少两个候选 PID 的采集共 22 次，最多 4 个候选 PID。`total_fd_dir_exists=63`，但 `total_fd_dir_readable=0`、`total_fd_dir_searchable=0`、`total_fd_glob_matches=0`、`total_fd_readlinks_succeeded=0`。`verified_fd_probe_polls=0`、`incomplete_fd_probe_polls=22`，22 个错误均为 `fd_probe_no_access`。

这意味着目标进程的 FD 目录能够被识别为存在，但本次 root shell 无法读取或遍历。**本轮的空 shared_links 没有 IPC 阴性证据价值。** `su -c "id -u"` 返回 0 只证实有效 UID，不保证内核 capability、procfs ptrace 可见性或 SELinux 授权。现有记录不足以唯一确定限制来源。

新增单次**不重启应用**的权限自检，应用需正处于运行状态：

~~~powershell
git pull
python .\experiments\capture_shared_pipes.py --diagnose-access
~~~

此选项在同一个 `su -c` shell 中比较根 shell 自己的 `/proc/$$/fd` 和已确认的应用主 PID 的 `/proc/PID/fd`，只输出双方的计数和分类状态；不读取 FD 内容，不输出软链接原始指向，不调用 `am force-stop` 或 `monkey`。不能同时指定 `--launch`。

- `target_fd_denied_or_hidden`：同一 root shell 能读取自己的 FD，但无法读取目标应用的 FD。后续优先恢复原版代码调用链，无需继续重复相同的采样。
- `root_shell_self_fd_check_failed`：连 root shell 自身 FD 都无法读取，应先检查 root shell 环境。
- `target_not_running`：没有观察到正在运行的目标主进程。手动打开应用后再运行一次单次诊断即可。
- `target_fd_readlink_accessible`：目标 FD 在诊断瞬间可以读取，仍需另行检查 IPC 发生时段。

确认访问限制之前不建议重复进行 18 秒自动重启采集，也不需要修改 SELinux 策略或应用数据。
