# 中国移动 12.5.5：SecNeo sw/bs 的进程身份守卫

2026-10-24。证据全部来自之前保存的原版中国移动 12.5.5 APK 及其同次设备诊断记录。固定 APK SHA-256：`6282d2cf05f76f37a60fff322bcf0d6f1d876829e5c9c4eae5cdd93b7a972a83`；内层 `libDexHelper.so` 通过原版 RC4/XOR 复原后，完整 SHA-256：`b0d42eb0d86a7fdd3c4e5669c46376d0d4c041da5adb3f5d0e3ccbe9f369ef54`。使用对原版 ELF 的直接 `llvm-objdump` 反汇编复核下列机器指令和跳转目标。

本篇接续[Service 绑定条件与 Manifest](12.5.5-secneo-messenger-service-binding.md)。此前已经确认默认 `H.PC_FLAG="255"`，`sw(Context,int)` 在参数 bit0=1 时提前返回，`bs(Context,int)` 在 bit1=1 时提前返回。本篇进一步恢复配置位**允许继续执行后**的真实进程身份守卫。

## 1. 两个 Native 方法调用同一个进程身份函数

| 位置 | 原版 AArch64 数据流 | 精确分支 |
| --- | --- | --- |
| `0x2C46C` | `tbnz w3,#0,0x2C8AC` | sw 参数 bit0=1 时跳过 |
| `0x2C47C–0x2C480` | `ldrb w8,[x8,#0xc]; cbz w8,0x2C8AC` | sw 运行时对象 `+0x0C` 字节为零时跳过 |
| `0x2C494–0x2C498` | `add x0,x8,#0x40; bl 0x2BF68` | 传入运行时配置的期望进程名，调用身份函数 |
| `0x2C49C` | `cbnz w0,0x2C8AC` | sw 检查返回非零时跳过 |
| `0x2C90C` | `tbnz w3,#1,0x2C930` | bs 参数 bit1=1 时返回 null |
| `0x2C924–0x2C928` | `add x0,x8,#0x40; bl 0x2BF68` | bs 调用同一个检查函数 |
| `0x2C92C` | `cbz w0,0x2C964` | bs 检查返回零才继续 |
| `0x2C970–0x2C974` | `ldrb w8,[x8,#0xc]; cbz w8,0x2C930` | bs 运行时对象 `+0x0C` 为零时返回 null |

这证明 `sw` 和 `bs` **共用原生 `0x2BF68` 检查函数**；调用前都读取运行时对象的 `+0x40` 字符串区域作为函数参数。两者检查 `+0x0C` 字节的先后顺序略有区别，但都要求其非零才能进入后续有效路径。

## 2. 0x2BF68 真实读取 /proc/当前PID/cmdline

原版 `0x2BF88/0x2BF8C` 令 `x9=0x124103`，对应经过 JNI_OnLoad XOR 变换后的原版可打印字符表 `0x1240F4+0x0F`。从原版指令取 `LDRB` 的立即数，直接得到两段字符串：

- `0x2BF98..0x2BFC4`，六处 `LDRB W8,[X9,#imm]` → **`/proc/`**
- `0x2BFD0..0x2C008`，八处同类 `LDRB` → **`/cmdline`**

在它们之间，函数直接执行三条经机器字验证的 AArch64 系统调用：

- `0x2C01C–0x2C020`：`mov x8,#172; svc #0`，`getpid`。
- `0x2C194–0x2C198`：`mov x8,#56; svc #0`，`openat`。
- `0x2C1DC–0x2C1E0`：`mov x8,#63; svc #0`，`read`。

中间 `0x2C048..0x2C140` 将 PID 转成十进制数字并组装路径，因而读取的是 **`/proc/<自身 PID>/cmdline`**。后续字节比较循环以调用方提供的字符串为条件。返回路径存在 `w0=0`（`0x2C434`）、`w0=1`（`0x2C2B8`）、`w0=2`（`0x2C42C`）和 `w0=3`（`0x2C400`）等指令；本轮已恢复上述四个返回码的主要静态触发条件；没有证据证明这些分支都在目标设备实际执行过。

它是一个**进程命令行／进程身份检查**，不能根据 `/proc` 字样就归为 Root、Frida 或 DEC 检测。

## 3. 已复原四种返回码与 `:rs` 特殊路径（2026-10-25 更新）

本轮重新直接反汇编固定哈希原版 ELF 的 `0x2C1F8–0x2C438`。从原版 `LDRB` 指令两次恢复字符串 `:rs`，分别位于 `0x2C200/0x2C208/0x2C210` 和 `0x2C21C/0x2C224/0x2C22C`，两个构造序列均由实际可打印字符表解码。

| 返回码 | 原始代码证据 | 对应的静态条件 |
| --- | --- | --- |
| 1 | `0x2C2B8: mov w0,#1` | 进程命令行命中专门检查的 `:rs` 字符串路径 |
| 2 | `0x2C38C cmp w10,#':'`、`0x2C390 b.eq 0x2C42C` | 特殊路径未截获，后续冒号扫描命中 `:` |
| 3 | `0x2C1B4`、`0x2C3A0`、`0x2C3C8`、`0x2C400` | 文件打开失败、期望名称缺失或不匹配等分支 |
| 0 | `0x2C3A8`、`0x2C3E4` → `0x2C434` | 期望名称为空，或实际名称前缀在期望长度内匹配 |

**重要修正：最后的名称判断是前缀匹配。** `0x2C3E0` 比较已经检查的字符数与期望字符串长度；`0x2C3E4` 在计数达到时直接跳到返回 0 的 `0x2C434`。逐字节比较发生在 `0x2C3E8–0x2C3F8`，没有验证实际命令行此时是否已经结束。即使实际名称在期望字符串后还带有额外字符，仍可能匹配成功，但前面的特殊字符串、冒号检查需要先通过。

`:rs` 是原版硬编码的字符串片段。它的存在不能证明它属于 `IsoService` 或某个已经建立的服务进程。本轮只验证原版静态分支，尚无设备执行记录。更新后的[身份审计工具](../tools/audit_inner_h_process_identity_gate.py)还验证返回码、条件跳转和 `:rs` 的原始字符来源，合成回归测试检测篡改指令。

## 4. 结合运行时配置，Service 绑定的必要条件进一步收窄

对于已恢复的 `bs(Context,int)` 源代码路径，至少需要：

1. Native 收到的 Context 非空，参数 bit1=0；
2. `0x2BF68` 返回零；
3. 运行时配置对象 `+0x0C` 字节非零；
4. 后续 JNI `FindClass`、`Intent(Context,Class)` 和 `Context.bindService` 都成功。

初始 Java `PC_FLAG=255` 的 bit1=1，直接阻止到达条件 2。即使该值后来变化，其余守卫也必须分别得到证据。对于 `sw`，bit0=0、运行时字段非零、进程身份函数返回零同样是已确认条件。

以前已恢复的 `H$a.handleMessage(what=1000) -> H.he(Message.arg2)` 说明原版存在接收并处理消息的代码，尚未证明任何同轮绑定或回调确实执行，更不能把发送端 `arg1=PID` 当作接收端 `arg2` 的来源。

## 5. 原版初始化中 +0x0C 字节已经闭合为 1

对最初未知的运行时对象完成了原版 ELF 寄存器与重定位追踪：

| 地址 | 直接验证的指令／关系 |
| --- | --- |
| `0x151DC/0x151E4` | `adrp x8,0x12a000; add x8,x8,#0x684`，建立对象 **`0x12A684`** |
| `0x151EC–0x151F4` | 清零对象的初始字段 |
| `0x15208` | `ldrb w10,[x24,#0x48a]`，直接读取原始内嵌配置对象 `0x12A440+0x4A=0x12A48A` |
| `0x15214` | `cbz w10,0x15264`，配置为 false 时跳过初始化写入 |
| `0x15210` | `x25=0x12A689`，指向对象偏移 `+5` |
| `0x15240–0x15250` | `mov/movk w13,#0x01000101; stur w13,[x25,#6]`，按小端写入对象偏移 `+11..+14` |
| `0x15298–0x152A4` | 通过原版 RELATIVE 重定位 `0x123BD8→0x128008`，把 `x8=0x12A684` 发布到运行时全局指针槽 |
| `0x2C47C/0x2C970` | 守卫通过该指针槽取得对象，再读取其 `+0x0C` |

之前已核验原版 XOR `0xAC` 的 MessagePack 数据流：`0x14C2C` 对 `+0x4A` 的解码布尔值为 **true**。本轮再次直接核对原始数据流字节，序列化偏移 `+63` 解码为 `0xC3`（MessagePack true）。因此初始流程正常执行时，`0x15250` 写入的 `0x01000101` 小端第二字节是 `1`，正好落在 **`0x12A684+0x0C=0x12A690`**。

**新的限定结论**：该运行时身份对象 `+0x0C` 字节的**初始值为 1**，属于已确认的原版静态初始化数据流；后续线程或反射是否改写它仍没有动态证据。它与前面研究的 `0x12A440+0x17C=0x12A5BC` 是不同对象或不同字段，不能混用。

结合 `PC_FLAG="255"`，默认 Java→Native 入口首先被参数位阻断。若假设运行时有人清除了这些位，原版初始 `+0x0C=1` 允许继续通过此处，但仍需 `0x2BF68` 的**实际返回值为 0**，才能进一步执行 `bindService`。

## 6. 已保存设备证据的覆盖范围

原版诊断 ZIP 自带的 `04-apk-paths.txt` 在该次采样中只有**一个 APK 安装路径，文件名为 `base.apk`**，没有列出安装的 split APK；固定原版 base Manifest 内 78 个 service 组件不含任何以 `IsoService` 结尾的名称。此处仅证明诊断记录的安装路径列表和 base Manifest，未检查 Android 当前运行的动态组件状态。

另一份已保存的重启 Logcat 没有出现文本 `IsoService` 或 `unbindService`；其中两处常规 `bindService` 警告对应其他应用/框架调用栈，未提供 SecNeo 绑定证据。**Logcat 缺少某文本也不能证明该操作一定没有执行。** 用户无需为重复这一观察重新启动 App。
