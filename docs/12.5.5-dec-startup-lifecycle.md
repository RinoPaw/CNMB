# DEC 启动路径的完整类定义扫描与生命周期回调（12.5.5）

证据范围：与 [前一份 Dex 表报告](12.5.5-dec-dex-callgraph.md)相同的 SHA-256 固定样本，直接读取原版 `libdatajar.so` 的 SO 文件偏移。以下结果来自只读验证脚本 `tools/audit_dec_callers.py`。

## 一、被恢复片段的覆盖率

| 项目 | 已验证 |
| --- | ---: |
| 连续有效 `class_defs` | 16,526 |
| 编码 `encoded_method` | 57,366 |
| 含有效 `code_item` 的方法 | 55,713 |
| 方法体解析失败 | 0 |
| 16-bit 对齐 `invoke-static{,/range} startCheck` **候选** | 1 |

唯一候选是 `DECApp.intiDECabcOnCreate`，方法 ID **62487**，SO 文件偏移 **`0x1c20672`**，编码 `71 00 20 f4 00 00`。该位置经针对性指令核对，是实际 `invoke-static` 指令。候选扫描覆盖所有 55,713 个已恢复的方法体，但**尚未构建覆盖所有 Dalvik 变长指令及 payload 的完整反汇编器**；扫描结果应准确表述为“唯一候选”，不能扩展为“整个 APK 唯一入口”。

`DeviceEnvironmentCheck` 的 type ID 为 **17421**，`startCheck` 方法 ID 为 **62496**。在 16,526 个有效类定义中，**没有** class_idx=17421，因此 `startCheck()` 的方法体仍未恢复。

## 二、主进程判断路径：`DECApp`

`onCreate()V`（方法 ID 62489）调用 `intiDECabcOnCreate`（62487）。后者首先执行：

```text
0x1c20608: invoke-static       DECApp.isMainProcessDECabc
0x1c2060e: move-result        v0
...
0x1c2065c: if-nez             v0, +3
0x1c20660: return-void
...
0x1c2066c: invoke-virtual     registerActivityLifecycleCallbacks
0x1c20672: invoke-static      DeviceEnvironmentCheck.startCheck()
```

故 **v0=0 时该方法直接返回**；非零时会注册生命周期回调并调用 `startCheck()`。其余指令还包括调试日志的拼接；调用点的 Dex 方法索引和分支字节均已验证。

`isMainProcessDECabc()`（62488）的已恢复指令调用：

- `myPid()`（method_id 1073）
- `java.io.File` 的构造与 `exists()`（62603、62608）
- `java.io.FileReader`、`java.io.BufferedReader` 的构造（62623、62596）
- `BufferedReader.readLine()`、`String.trim()`（62598、62798）
- `getPackageName()`、`String.equals()`（34、62780）

还存在明文 `isMainProcess cmdline = `。由这些指令可确认其读取文件中的进程名、与应用包名比较，用于决定调用后续环境检测；**路径常量位于无法读取的早期字符串 ID 区**，因此尚未从该方法恢复确切的 `/proc/...` 路径。

这段行为只决定**主进程范围**，不证明任何 Root 检查条件。

## 三、`DECApp$1` Activity 生命周期回调

该内部类 class_idx **17417**，类定义 SO 偏移 **`0x1e9750`**，其中方法体全部可解析：

| 方法（method_id） | 已验证的 DEC 目标调用 |
| --- | --- |
| `onActivityCreated` (62479) | `DECRunning.saveActivity` (62494) |
| `onActivityDestroyed` (62480) | `DECRunning.removeActivity` (62493)，`DECRunning.onActivityDestory` (62492) |
| `onActivityResumed` (62482) | `DECRunning.setForegroundActivity` (62495) |
| `onActivityStopped` (62485) | `DECRunning.getForegroundActivity` (62491)，`setForegroundActivity` (62495) |
| `onActivityPaused` (62481) | 方法体仅 `return-void` |
| `onActivitySaveInstanceState` (62483) | 方法体仅 `return-void` |
| `onActivityStarted` (62484) | 方法体仅 `return-void` |

已恢复代码表明 DEC 维护 Activity 列表及当前前台 Activity；被调用的 `DECRunning` 具体方法实现仍未恢复。名称 `onActivityDestory` 的拼写保留原始 Dex。

## 四、全 SO 字符串交叉检查

`libdatajar.so` 中明文类描述符 `Lcom/a/b/c/DeviceEnvironmentCheck;` 仅出现一次（`0x3febc3`），`getCheckResult` 在 `0x7ec143e` 的另一组字串中。它们之间目前**没有**可验证的方法归属或调用关系。

在已检索的几个原版 SO 中，ASCII 子串 `frida` 的命中分别属于 `friday`、`blackfriday` 等普通字符串；**这些命中不构成反 Frida 代码证据**。搜索时应检查完整词与字串上下文，不能拿 `frida` 作为裸子串就宣称发现检测机制。

## 五、复核与边界

```powershell
python .\tools\audit_dec_callers.py .\path\to\base.apk
# 也支持原始诊断 ZIP 或从 APK 提取的 libdatajar.so
```

该工具依赖同目录的 `inspect_dec_tables.py`，固定样本哈希校验通过后才能运行；对方法引用和条件分支做字节级断言，验证不通过时应报错退出。

**下一步关键障碍**：需要定位另一个保存 `DeviceEnvironmentCheck` 类定义的代码来源，才有机会获得 `startCheck` 实现。原版 SO 中的孤立字串、方法引用和完整调用点数量都无法替代方法体证据。
