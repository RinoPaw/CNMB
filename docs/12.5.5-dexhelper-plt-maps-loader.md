# 中国移动 12.5.5：`libDexHelper` 构造函数的 PLT、`sscanf` 与进程映射加载链

核验日期：2026-10-23。原始证据来自 SHA-256 固定的中国移动 12.5.5 APK 和其中两份 ARM64 ELF。工具：[tools/audit_dexhelper_plt.py](../tools/audit_dexhelper_plt.py)。没有使用社区逆向结论，也未动态注入或修改原版客户端。

## 一、精确补全之前未知的两个 PLT 调用

此前研究已由 `DT_INIT_ARRAY` 与 `R_AARCH64_RELATIVE` 证明 `libDexHelper.so` 的 `0x4780` 是原版 ELF 构造函数。[前期构造函数报告](12.5.5-dexhelper-native-constructors.md)。

通过 `PT_DYNAMIC` 中的真实 `DT_SYMTAB=0x16d000`、`DT_STRTAB=0x16f000`、`DT_JMPREL=0x2730` 和 24 条 `R_AARCH64_JUMP_SLOT`（类型 1026）重定位，现可将两次调用直接归属于具名导入：

| 构造函数中调用点（ELF VA） | 原版 `BL` 目标 PLT | JUMP_SLOT/GOT 槽 ELF VA | 实际解析的函数 |
|---|---|---|---|
| `0x4850` | `0x2a30` | `0x14f80` | **`dlopen`** |
| `0x485c` | `0x2a50` | `0x14f90` | **`dlsym`** |
| `0x4940` | `0x33f8` | 本地分支，无 PLT | 本库原生辅助加载函数 |

原版 `0x4848` 的 `add x0,...,#0xa60` 指向静态串 `libc.so\0`（`0x4a60`），`0x4844` 设置 `w1=2`；因此 `0x4850` 的具体调用参数是 **`dlopen("libc.so", 2)`**。紧接着 `0x4858` 将 `x1` 设为字符串 `sscanf\0`（`0x4a68`），`0x485c` 调用 **`dlsym(handle, "sscanf")`**，结果随后在 `0x4878` 写入全局区域 `0x15038`。这一系列可由真实导入表、指令机器码和原版 ASCII 数据同时核对。

尤其要注意：`libDexHelper` 的 section-header `.dynsym` 指向一个原版中无可用名称的区域。若单纯运行 `readelf -Ws` 可能只看到大量空符号。**应以程序头 + `PT_DYNAMIC` 中的 `DT_SYMTAB`、`DT_STRTAB` 与 `DT_JMPREL` 为权威，才能得到上述具名导入和真实 PLT 关系。**

## 二、`0x33f8` 辅助函数确实读取 `/proc/self/maps`

根据 `0x4940` 的直接 `BL` 跳转，进入本库 `0x33f8`。其具体原版调用关系如下：

| 在 `0x33f8` 内的调用点 | 已解析外部函数/方式 | 从原版参数指令证明的作用 |
|---|---|---|
| `0x3574` → PLT `0x2a60` | **`fopen`** | `fopen("/proc/self/maps", "r")`，路径 `0x4a08`，模式 `0x4a18` |
| `0x35d0` → PLT `0x29a0` | **`fgets`** | 从文件逐行读取文本到栈上缓冲区 |
| `0x3600` | **`blr x8`** | `x8` 来自构造函数保存的 `sscanf` 指针，格式为 `%lx-%lx %s %s %s %s %s`（`0x4a20`） |
| `0x3628` → PLT `0x2a80` | **`fclose`** | 关闭已打开文件 |
| `0x370c`、`0x3884` | **`mmap`** | 建立内存映射；具体后续段内容仍需完整数据流 |
| `0x4088`、`0x40c4` | **`mprotect`** | 以从 ELF 段标志计算的权限调整映射 |

指令 `0x35dc` 为 `ldr x8,[x25,#0x38]`，`0x3600` 为 `blr x8`；构造函数在 `0x4878` 将 `dlsym` 返回值写入相应全局槽。**这说明调用链中动态解析的 `sscanf` 确实被用于解析 `/proc/self/maps` 文本**。这项结论现有完整的 ELF 导入符号、调用编码、间接函数指针保存/读取和字符串参数证据。

辅助函数后续还会解析 ELF Program Header、建立 `mmap` 映射、导入其他原生库和修正页面权限。尤其 `0x450c` 又通过 PLT 调用 `dlopen`，其 `x0` 来自已解析 ELF 中的动态依赖字符串偏移；`0x454c`、`0x456c` 调用本库的本地函数 `0x2cd0`，说明此处还存在与 ELF 符号/重定位相关的进一步工作。**辅助装载链已经有直接字节证据，仍需继续拆解 `0x2cd0` 的具体语义。**

## 动态符号表的另一个陷阱：`JNI_OnLoad` 是字符串，没有可见静态导出

对原始 `DT_HASH` 中的 `nchain`、真正的 `DT_SYMTAB` 与 `DT_STRTAB` 做完整枚举：

| 原版库 | HASH 桶 | nchain / 符号槽数 | 名称为空的槽 | 静态 `JNI_OnLoad` 符号 |
|---|---:|---:|---:|---|
| `libDexHelper.so` | 197 | **239** | **207** | 无 |
| `libdexjni.so` | 17 | **29** | **3** | 无 |

虽然两份 SO 都含有 ASCII 字符串 `JNI_OnLoad`，且它们的 9,030 B 共用尾段具有相同字节，在原版动态符号表里仍**没有名为 `JNI_OnLoad` 的可见符号**。所以不能据这个字符串宣布当前 ELF 有公开的 `JNI_OnLoad` 导出入口。加固载入后可能存在动态恢复的代码或符号，尚未验证。

特别是 `libDexHelper.so` 的哈希链声明 239 个符号槽，却有 207 个空名称槽。这是原版 ELF 动态符号结构的事实，不应把填充、损坏或其他保护策略强行确定为某一种解释。

## 三、两个 SO 共用的完全相同调用链

`libDexHelper.so` 的 `[0x295a,0x4ca0)` 与 `libdexjni.so` 的 `[0x95a,0x2ca0)`，原版已有 **9,030 字节精确相同**的证明。本轮重定位和调用分析进一步确认：

- 后者加载构造函数为 **`0x2780`**，调用 `dlopen` 在 `0x2850`、调用 `dlsym` 在 `0x285c`，本地辅助函数入口为 **`0x13f8`**。
- `libdexjni.so` 的字符串 `libc.so` 位于 `0x2a60`、`sscanf` 位于 `0x2a68`、`/proc/self/maps` 位于 `0x2a08`。
- 后者核心逻辑的上述所有 PLT 调用点，相比 `libDexHelper.so` 均为 **减去 `0x2000`**，两份原始机器指令编码相同。

二者共有**相同的 ELF 装载引导逻辑**。但以前的设备采样只确认早期出现了 `libDexHelper.so`；没有观察到 `libdexjni.so`，所以不能宣布后者在实测进程中执行。

## 进一步确认：ELF 依赖加载和重定位处理

这套装载链的下一阶段也已经解码，并加入自动断言：

- **`0x44ec`** 比较动态条目标签是否为 `1`（`DT_NEEDED`）。`0x44f4` 读取依赖库名偏移，`0x4508` 加上字符串表基址，`0x450c` 通过原始 PLT 再次调用 **`dlopen(dependency_name, 2)`**。
- **`0x454c` 和 `0x456c`** 都跳转至本地函数 **`0x2cd0`**。该函数内部，`0x2e20` 调用 `dlsym`，`0x2e28` 调用 `dlerror`，`0x2e34` 调用 `strstr`，`0x2e90` 调用 `strcmp`，其 ELF 导入名由真实动态重定位表交叉验证。
- 在 `0x2cd0` 的分支中，原版指令直接比较重定位类型 `257`（`R_AARCH64_ABS64`）、`1024`（`COPY`）、`1025`（`GLOB_DAT`）、`1026`（`JUMP_SLOT`）、`1027`（`RELATIVE`）等数值；对应含有目标地址计算和 `str` 存储操作。

结合前一节的 `/proc/self/maps` 读取、ELF Program Header 解析、`mmap`、`mprotect`，**本库具有手动装载 ELF 依赖及处理重定位的具体原版调用链证据**。尤其 `0x2CD0` 可定位为 ELF 重定位处理函数。各条件分支是否实际可达及指向哪段待装载内存，仍需继续验证。

两份库相应地址再次具有 `-0x2000` 关系：`libdexjni.so` 的依赖库加载调用点是 `0x250c`，本地重定位函数为 `0x0cd0`。当前仍没有发现把这些动作连到 `DeviceEnvironmentCheck.startCheck()` 或辅助 Java 进程创建的证据。

## 两份构造引导程序的 24 个直接导入

从各自的 `DT_JMPREL` 和原始 `DT_SYMTAB` 解出的 **24 个 PLT 导入名称与顺序完全一致**：

`dlerror`、`fgets`、`memcpy`、`__cxa_finalize`、`lseek`、`mmap`、`abort`、`__stack_chk_fail`、`strstr`、`read`、`dlopen`、`__cxa_atexit`、`dlsym`、`fopen`、`memset`、`fclose`、`isprint`、`strcmp`、`sprintf`、`pread`、`strlen`、`open`、`mprotect`、`close`。

其中没有 `fork`、`vfork`、`clone`、`execve`、`posix_spawn`、`system` 或 `popen` 的**直接 PLT 导入**。结合上一轮 `libDexHelper` 现存可执行 `PT_LOAD` 中没有直接 `svc` 指令的验证，当前可以把“构造函数通过这些已知 PLT 导入直接创建观察到的辅助进程”列为**未找到证据**的路径。仍不能排除 `dlsym` 间接解析、另一库、运行时恢复的代码或其他机制。

## 四、研究边界：不能过度解释

这轮证据将 `libDexHelper:0x4780 → dlopen/dlsym → 0x33f8 → /proc/self/maps / sscanf / mmap / mprotect` 的**静态调用链**确定到了原版函数地址和机器码。

- `/proc/self/maps` 在此确有**读取并解析的调用链**，但其用途有可能包括寻找自身映射与 ELF 装载，**还不能把它认定为 Frida、Root 或 DEC 检测**。
- 这条链上没有直接恢复 `fork` / `execve` 的导入调用；无法因此排除其他 native 入口和运行时生成的进程创建代码。
- `DeviceEnvironmentCheck.startCheck()` 实现、`DECMsgDialog` 决策条件、两轮重复的独立 `RuntimeInit` 的创建者，仍缺直接证据。
- 本次自动验证器是**哈希固定、只读的静态分析**。运行时调用是否可达、何时执行，需要设备追踪证据或补充原版控制流分析。
