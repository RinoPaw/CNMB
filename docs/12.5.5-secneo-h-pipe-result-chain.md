## 一、H Java 代码：读取 FD、检查进程、通过 writeUTF 回传结果

| DEX code_item 偏移 | 原始定义 | 关键证据 |
| --- | --- | --- |
| \`0x4e60\` | \`H.main(String[])\` | 要求 \`args.length == 4\`；\`args[1]\` 调用 \`Integer.parseInt\` 后交给 \`ParcelFileDescriptor.adoptFd\`；\`args[3]\` 作为 flags |
| \`0x46a8\` | \`H.b(int)\` | 读取 \`/system/bin/app_process\` 的一个字节并关闭输入流；\`SystemClock.sleep(2000)\`，调用 \`H.a(flags)\` |
| \`0x4328\` | \`H.a(int)\` | 打开 \`/proc/self/status\`，分别具备 \`TracerPid:\`、\`PPid:\` 的前缀匹配、\`substring/trim/parseInt\` 读取分支 |

原始字节码的具体调用点，以方法 code_item 起点后的**相对字节偏移**记录：

- \`H.main+0x2e\` 获取参数 \`args[1]\`，\`+0x32\` 调用 \`Integer.parseInt\`，\`+0x3a\` 调用 \`ParcelFileDescriptor.adoptFd\`。
- \`H.main+0x44\` 获取参数 \`args[3]\`，\`+0x48\` 转换为整数，\`+0x5a\` 调用 \`H.b(int)\`。
- \`H.main+0x6a/+0x70\` 依次构造 \`ParcelFileDescriptor.AutoCloseOutputStream\` 和 \`DataOutputStream\`；\`+0x76\` 使用 \`Integer.toString\`；\`+0x7e\` 调用 \`DataOutputStream.writeUTF\`；\`+0x84\` 关闭输出流。
- \`H.b+0x5e\` 设置 \`2000\` 毫秒延迟；\`+0x62\` 调用 \`SystemClock.sleep\`；\`+0x68\` 调用 \`H.a(int)\`。
- \`H.a+0x40\` 的 \`if-nez p0\` 分支与 \`+0x78/+0x7a\` 的 \`p0==1\` 分支共同确定：**flags=0 读取 TracerPid，flags=1 读取 PPid**；它们分别在 \`+0x76\` 和 \`+0xae\` 返回解析的整数。

此前的 [原版 execl 参数审计](12.5.5-inner-app-process-argv-thread-chain.md) 已直接恢复 \`--write-fd <动态十进制 FD> --flags 0\`；配合这次 Java 参数与分支数据流，可以确定**原版默认 flags=0 路径回传进程的 TracerPid 数值**。Java \`writeUTF\` 使用二字节长度前缀与修订 UTF-8 编码；在这里只能说原版代码调用了该 API，无法保证设备某轮一定写入成功。

## 二、原版 native：把同一 pipe 的读端交给 JNI DataInputStream

在内层 \`libDexHelper.so\` 的独立线程函数 \`[0x59700,0x5b45c)\` 中，按 ELF 原始机器码和真实 FD 寄存器来源恢复：

| ELF VA | 直接观察的指令或 API |
| --- | --- |
| \`0x5a3d0\` | \`pipe@plt\`，输出 FD 数组位于 \`[x29-0x70]\` |
| \`0x5a3e0\` | \`ldp w19,w22,[x29,#-0x70]\`，分别取得读端与写端 |
| \`0x5a418\` | 第一次 \`fork\` |
| \`0x5a440–0x5a444\` | 首次 fork 的父端关闭 \`w22\`（管道写端） |
| \`0x5a454\` | \`waitpid\` |
| \`0x5a468\` | 从 \`[sp+0x20]\` 恢复先前保存的读端 FD |
| \`0x5a8c8\` | \`ldr w3,[sp,#0x20]\`，将该 FD 交给 Java 方法调用的第一个参数 |
| \`0x5a8dc\` | \`BL 0x2a314\`，JNI \`CallStaticObjectMethodV\` 封装调用 |

JNI 类名、方法名和签名没有依赖猜测：内层 ELF 的 \`0xf1988\` 和 \`0xf19a8\` 保存经可打印 ASCII 表解码的 \`android/os/ParcelFileDescriptor\`、\`(I)Landroid/os/ParcelFileDescriptor;\`；\`0x5a844–0x5a874\` 的逐字符 \`LDRB/STRB\` 构造 \`adoptFd\`。

其后原版逐字节构造和 JNI 虚表调用继续证明：

1. \`android/os/ParcelFileDescriptor$AutoCloseInputStream\` 构造（原始编码字符串来源 \`0xf19cd\`）。
2. \`java/io/DataInputStream\` 和构造函数 \`<init>(Ljava/io/InputStream;)V\`。
3. 构造 \`readUTF()Ljava/lang/String;\`，\`0x5ad04\` 间接调用 JNI \`GetMethodID\`，\`0x5ad18\` 调用 \`0x13dc4\`（最终使用 JNI \`CallObjectMethodV\`）。
4. \`0x5ae30–0x5ae34\` 使用 JNI \`GetStringUTFChars\`；\`0x5ae38\` 调用 \`atoi@plt\`；\`0x5ae3c\` 执行 \`cmp w0,#1\`，\`0x5ae40\` 执行小于 1 时跳转的条件分支。

因此可以从**同一份原版 ELF 的同一个 pipe FD 数据流**闭合：父端保留读端 → JNI \`ParcelFileDescriptor.adoptFd\` → \`AutoCloseInputStream\` → \`DataInputStream.readUTF\` → 将结果字符串转为整数 → 针对 \`>=1\` 的分支。配合 H Java 写端已经构成静态的两端证据。

## 三、2026-10-24 真实设备 FD 访问限制

第四轮 ADB 采样 \`polls=39\`，其中 22 次尝试扫描多个同 UID PID 的 FD；\`total_fd_dir_exists=63\`，但所有 FD 目录可读/可搜索、glob、readlink 计数均为 0，记录 22 次 \`fd_probe_no_access\`。

后续显式 \`--diagnose-access --launch\` 进一步确认：

- root shell 自身 \`probe_count=1\`、\`fd_dir_readable=true\`，\`fd_readlinks_succeeded=3\`。
- 目标中国移动主进程 \`probe_count=1\`、\`fd_dir_exists=true\`、\`fd_dir_readable=false\`、\`fd_dir_searchable=false\`、\`fd_readlinks_succeeded=0\`。
- 诊断结果 \`target_fd_denied_or_hidden\`。

这证明本次 Root Shell 可读自己的 FD，却不能枚举目标 App 的 FD；尚不能唯一认定阻断来自 SELinux、procfs、ptrace 权限或其他内核约束。旧实验中的 \`shared_links=[]\` 均**不构成没有 IPC 的证据**。后续优先恢复原版静态调用链，不再重复相同的设备 FD 扫描。

## 四、已经闭合与仍未闭合的证据

已闭合的**原版静态机制**：原生线程 \`pipe/fork/execl\`，默认 H 与 \`--write-fd/--flags 0\`，H Java 读取 \`TracerPid\` 并通过 \`writeUTF\` 写回 FD，原生父端在同一 pipe 的读端使用 \`readUTF\` 读取并解析整数，按 \`>=1\` 判断。

仍然没有证明：每轮设备上的实际写入/读取是否完成，具体观察到的辅助 PID 是否来自这条 fork 路径，以及 \`>=1\` 分支是否直接触发 \`DeviceEnvironmentCheck.startCheck()\`、\`DECMsgDialog\` 或应用终止。**这个已恢复的检查针对 TracerPid，不能直接宣称是 Root 检测或反 Frida 崩溃的触发源。**
