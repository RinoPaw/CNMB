# 12.5.5：原生加载阶段、嵌套风险 SDK 与 `0x978` 崩溃证据

日期：2026-10-22。所有偏移均基于用户提供的**原版 APK/ELF 字节**，没有执行 Frida 注入或修改 APK。

本报告可以使用 [tools/inspect_native_loader.py](../tools/inspect_native_loader.py) 对原始诊断 ZIP / APK 及完整 Tombstone 复核。研究工具只输出文件哈希、原生 ELF Program Header、字面量偏移和脱敏后的内存映射摘要，**不复制原始设备日志**。

## 一、样本身份与 ELF 加载布局

APK SHA-256：`6282d2cf05f76f37a60fff322bcf0d6f1d876829e5c9c4eae5cdd93b7a972a83`。

| APK 中的文件 | SHA-256 | 关键的 `PT_LOAD` 文件区段 |
|---|---|---|
| `libDexHelper.so` | `6b5abe051e75d630d5447785d1f1a9f480b2c636f2874a7494767cfcde2ac4db` | `r-x` 19,616 B；另有 `rw-` 1,218,272 B |
| `libdexjni.so` | `f567dde1e581483f7da6680d87183b522493b5109f19ea27bf388fd80aec9199` | `r-x` 11,424 B；`rw-` 4,453,344 B |
| `libdexvmp.so` | `1003c91df71d44bb8d4e44dd0b89e4d708bf4422d27646863155b58e2ef65cfb` | `r-x` 469,128 B；另有 `rw-` 与一段 `r-x` |
| `libdatajar.so` | `8b0777aeeedb1d95041fb8b5a900735d607505f802255227a82c83225d8bbf81` | `r-x` 1,936 B；`rw-` 158,716,508 B；另有 `r-x` 2,640 B |

以上仅描述静态 ELF 布局，无法由此确定 Java 类恢复到内存的具体算法与时刻。`libDexHelper.so` 的原始字节还包含 `JNI_OnLoad`、`/proc/self/maps`、`liblinkerstub.so` 字符串，偏移分别为 `0x49f8`、`0x4a08` 及多个位置。这些是字面量命中，**不是已证明的函数调用**。

## 二、澄清：`libZWRiskComm` 的 APK 条目其实是 ZIP 包装层

APK 内的 `lib/arm64-v8a/libZWRiskComm-v7_6_4r_61803305.so` 以 `PK\x03\x04` 开头，整体为 **1,032,651 B 的 ZIP**，内部只有一个同名路径条目，内容才是真实 **1,016,152 B 的 ARM64 ELF**：

- 外层 ZIP SHA-256：`77573bc82a269c51b5b9e034ab5de86300ba860a3b57c24457ffcb5c01af33ce`
- 内层 ELF SHA-256：`01bd6f4f048af96615d9013926d61ed15066cd8255b91445632a4fed4c628628`

**以下偏移均相对内层 ELF**。实际字节中确认存在：

| 精确 ASCII 字面量 | 内层 ELF 偏移 |
|---|---|
| `frida-agent` | `0x20191` |
| `frida-dump` | `0x20d9d` |
| `frida_agent_main` | `0x250cd` |
| `possible frida: loading` | `0x25ad9` |
| `kernel ptrace hooked` | `0x2556b` |
| `/system/bin/su` | `0x2176b` |
| `/proc/self/maps` | `0x28c9f` |

这些字符串支持该 SDK 包含针对 Root/Frida/注入环境的检查或诊断能力，但**单独的字符串不能证明方法被执行**。这个 SDK 的静态存在与 `DeviceEnvironmentCheck.startCheck()` 的调用关系也尚未证明。

## 三、`15:17` 的完整 `SIGSEGV 0x978` Tombstone

样本：用户提供的 `tombstone_18`，时间 `2026-10-22 15:17:01.793 +0800`，主进程 `com.greenpoint.android.mc10086.activity`，PID **20050**。

校验摘要：

- `SIGSEGV`，故障地址与 `PC` 同为 `0x978`；`LR=0`，`SP=0`。
- 解析到 **2,019** 条内存映射记录。
- 在五个重点 SO 名称（`libDexHelper`、`libdexjni`、`libdexvmp`、`libdatajar`、`libZWRiskComm`）中，映射列表**只出现了 `libDexHelper.so`**。
- `x19 = 0x75aa6cd870` 位于 `[0x75aa6b8000, 0x75aa7d2000)` 的匿名 `rwx` 内存区域，长度 **1,155,072 B**。Tombstone 在该地址附近确实显示 ARM64 指令数据。

**边界**：此 Tombstone 来自 Frida 17.5.2 服务端关闭后、手机尚未完全重启消除先前实验运行时状态的那一轮。因此它能帮助定位崩溃时的加载阶段，不能单独证明只要加载 `libDexHelper` 就必然崩溃，更不能证明它主动反 Frida。

同时，`x19` 位于匿名 `rwx` 区域只能证明该寄存器指向此区域；无法证明 `PC` 当时正在这段区域执行，也无法直接归属给某个 SO。

## 四、下一步的可验证假设

1. **加固初始化阶段异常**：崩溃时只记录到 `libDexHelper.so`，尚未观察到其他关注的原生库映射。优先检查初始化阶段的内存变化，以及 `libDexHelper` 的加载和是否在该阶段生成匿名可执行页。
2. **应用中另有反 Frida SDK**：`libZWRiskComm` 的内层 ELF 有明确标记，但该崩溃快照中没有相应库映射；需要有时间顺序的实际加载证据，不能将它当作崩溃直接责任方。
3. **DEC 方法体动态加载**：对已恢复的 14 组 Dex 类定义表全量核对，`DeviceEnvironmentCheck` 仍只有引用。后续应继续对实际加载阶段做只读取证，优先确定定义该类的载体来源。

## 复核命令

```powershell

```

## 五、待验证的 ADB-only 时间序列

新增 [experiments/capture_loaded_modules.py](../experiments/capture_loaded_modules.py) 记录真实启动期间的 `/proc/PID/maps` 摘要。它不会使用 Frida 或注入目标进程，采集模块名称、匿名可执行页数量、相对时间和 PID，可用于判断 `libdexjni`、`libdexvmp`、风险 SDK 是否曾在 DEC 弹窗前加载。仍需设备上的实际运行结果；瞬间映射/卸载的区域可能错过采样。

建议在干净重启并关闭 Frida 服务端的条件下执行，命令参见仓库 README。使用 `--launch` 会对目标应用执行 `am force-stop` 并由 `monkey` 重新启动；不会清除应用数据。

## 六、原始 ELF 构造函数的后续复核

静态验证 [`tools/audit_protector_constructors.py`](../tools/audit_protector_constructors.py) 已定位 `libDexHelper.so` 的首个 `DT_INIT_ARRAY` 函数为 **ELF VA / 文件偏移 `0x4780`**。该函数原始 ARM64 指令包含回溯匹配 ELF 魔数以及两个 PLT 调用。`libdexjni.so` 对应首个构造函数是 `0x2780`；两库可执行段末尾有 **9,030 个字节完全相同**。完整原始偏移、SHA-256 与动态重定位对应关系见 [构造函数专项报告](12.5.5-dexhelper-native-constructors.md)。

这一证据支持将 `libDexHelper` 的装载构造阶段列为优先调查位置，仍不能将运行时匿名 RWX 页或 `DeviceEnvironmentCheck.startCheck()` 直接归到这些已定位指令。
