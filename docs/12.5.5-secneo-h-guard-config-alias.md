# 中国移动 12.5.5：SecNeo H 正结果分支的配置字段来源与初始化值

原版核验日期：2026-10-24。研究仅使用之前上传的 `ChinaMobile-APatch-20261021-232128.zip` 内 `apks/01-base.apk`。原始 APK SHA-256：`6282d2cf05f76f37a60fff322bcf0d6f1d876829e5c9c4eae5cdd93b7a972a83`，恢复后的内层 `libDexHelper.so` SHA-256：`b0d42eb0d86a7fdd3c4e5669c46376d0d4c041da5adb3f5d0e3ccbe9f369ef54`。所有判断均为原始机器指令、ELF 重定位和静态编码配置的分析结论。

## 1. 已闭合：分支所读取的对象究竟位于何处

此前研究确认 `0x5ae44..0x5ae54` 在 `atoi >= 1` 后经全局指针读取运行时对象的 `+0x17c` 字节，但没恢复这条指针的赋值来源。此次根据原版 ELF 机器指令和 `R_AARCH64_RELATIVE` 重定位，确认完整数据流：

| 原版 ELF 地址 | 指令及效果 |
| --- | --- |
| `0x14a54`、`0x14a58` | `adrp x22,0x12a000; add x22,x22,#0x440`，构建 `x22=0x12a440` |
| `0x151d0`、`0x151d4` | `adrp x11,0x123000; ldr x11,[x11,#0xdc0]`，访问原始重定位项 `0x123dc0` |
| RELA `0x123dc0` | 类型 `R_AARCH64_RELATIVE`、addend 为 `0x128000`，目标是 BSS 指针槽 |
| `0x151e8` | `str x22,[x11]`，将 `0x12a440` 写入上述全局指针槽 |
| `0x5ae44–0x5ae50` | 读取同一重定位项 → 解引用 `[0x128000]` → 读取对象 `+0x17c` 的一个字节 |
| `0x5ae54` | `tbnz w8,#0,0x5af18`，检查该字节的 bit 0 |

因此经上述原版初始化路径建立的对象字段地址为 **`0x12a440 + 0x17c = 0x12a5bc`**（地址均为内层 ELF 虚拟地址；运行时还需叠加映射基址）。这是可直接核对的原始寄存器和指针赋值链。

**纠正旧假设：** 原版 `0x3af44–0x3af48` 使用 `adrp x12,0x12b000; strb w9,[x12,#0x17c]`，写入的确切地址是 **`0x12b17c`**。它与 `0x12a5bc` 不是同一静态 BSS 字节，不能当作此次检测条件的写入来源。另有重定位或指针动态替换需要单独证明；这次验证仅确定初始化时的来源。

## 2. 已恢复：原版配置中的 `+0x17c` 初始整数为 13

`JNI_OnLoad` 的 `0x14b08` 从内层 ELF 数据段 `0x12415b` 开始建立配置读取器；`0x14afc/0x14b0c` 计算得到读取回调 `0x2870c`。`0x28758` 和 `0x2878c–0x28798` 的原版指令使用 **`0xac` 异或每个字节**。

`0x14b28` 初始化读取器，之后按原始代码顺序执行 48 次配置读取调用。读取器处理 MessagePack 布尔值、整数与二进制长度/内容；二进制内容只用来推进流偏移，不公开原文。第 46 次配置读取（从 0 起索引 45）为：

```text
0x14d80: add x1,x22,#0x17c
0x14d84: add x0,sp,#0x40
0x14d88: bl 0x856ac
```

`0x856ac` 将解码的整数存为 32 位值（`0x85748: str w8,[x19]`）。它在解码流中的起始偏移为 **92**，该字节由原版 `0xa1 XOR 0xac = 0x0d` 恢复，MessagePack 正整数值为 **13**。后续配置项的长度解析也与原版代码调用数一致，排除了把数据片段错当成单独配置字段造成的偏移错误。

| 属性 | 原版初始化状态 |
| --- | --- |
| 静态对象地址 | `0x12a440` |
| 字段字节地址 | `0x12a5bc` |
| 存储类型 | 至少 32 位整数 |
| 解码初始值 | **13 / `0x0d`** |
| bit 0 | **1** |

`13` 属于**初始化值**，不应被当作所有时刻的设备运行值。原版还有大量依赖配置对象的检查路径，其他线程是否修改该字段及实际设备上的即时状态，仍待验证。

## 3. 原版初始配置下的正结果后续分支

根据前序[原生判定分支审计](12.5.5-secneo-h-result-guard-branch.md)：

- `0x5ae38` 接收 `GetStringUTFChars` 的返回指针并执行 `atoi`；
- `0x5ae3c–0x5ae40` 检查整数是否小于 1，符合时跳至 `0x5af6c` 清理路径；
- 在 `atoi >= 1`、且字段仍为初始值 `13` 时，`0x5ae54` 的 bit 0 检查**跳至 `0x5af18`**，不会进入跳向低地址 `0x1f8` 的异常指令；
- `0x5af34` 调用 `0x2616c`。返回值为 0 则跳 `0x5af6c`；否则 `0x5af44` 调用 `0x2682c`，其返回值低字节非零也跳 `0x5af6c`；两步符合条件后 `0x5af68` 调用 `0x26bc0`，同时令 `w1=1`；
- `0x2682c` 内部确实存在 `0x26930 → fopen@plt` 和 `0x269b0 → fgets@plt`，可确认这条辅助函数路径涉及文件访问。文件名、检查意义及后续处置暂不猜测。

这说明 `0x1f8` 异常分支受到一个**原版初始化为启用位的配置字段**控制。只有字段 bit 0 为 0，才会在 `atoi >= 1` 的情况下顺序进入该异常指令块。现有证据没有证明目标手机执行过该块，也没有证明它产生此前的 `SIGSEGV 0x978`，或与 DEC 弹窗直接关联。

## 4. 可复核性和研究边界

新增 [`tools/audit_inner_h_guard_config.py`](../tools/audit_inner_h_guard_config.py)，只用 Python 标准库：

~~~powershell
python .\tools\audit_inner_h_guard_config.py .\path\to\original-base.apk
~~~

也支持原版诊断 ZIP。工具强制检查原版 APK 与完整内层 ELF 的哈希、32 条关键 ARM64 原始机器指令、RELATIVE 重定位、48 次配置读取调用顺序、MessagePack 类型、目标整数值及后续辅助函数的实际 `BL` 地址，并拒绝内容不符的输入。合成单测位于 [`tests/test_audit_inner_h_guard_config.py`](../tests/test_audit_inner_h_guard_config.py)，不会把商业客户端二进制发布到仓库。

**仍缺证据**：运行时改变 `+0x17c` 的完整写入集合、`0x2616c/0x2682c/0x26bc0` 结果的上层语义、与 `DeviceEnvironmentCheck.startCheck()` 或 `DECMsgDialog` 的因果联系。后续优先分析这两个方向。
